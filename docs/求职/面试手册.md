# Synapse 面试手册

> 配套[简历项目描述](简历项目描述.md)使用。所有数字均可在 `docs/评测/评测基线与接入.md`、`eval-results/` 与 Git 历史中找到出处；被追问时优先报出处而不是背数字。

## 一、项目速览与数字卡片

一段话：Synapse 是面向代码仓库长任务的本地 Code Agent Harness——不是把 LLM API 包一层的聊天机器人，而是模型与真实开发环境之间的运行时控制层，统一治理上下文、记忆、工具授权和结果验证。

| 维度 | 数字 |
| --- | --- |
| 规模 | 约 113 个 Python 模块，653 个测试全绿，Python 3.11–3.14 |
| 接入 | 6 Provider（含 DeepSeek v4 双协议路由、fallback）、4 Planner（ReAct/Plan-Execute/Hierarchical/Swarm）、MCP stdio + Streamable HTTP |
| 上下文 | 四区预算（system 15% / core 50% / reference 25% / overflow 10%）、120K 字符软限、摘要式 compaction |
| 安全 | 5 级风险决策、14 类危险命令模式、12 类敏感路径、5 种沙箱后端、SSRF/注入防护 |
| 评测 | 冻结 20 题（gold-verified 入库，sha256 `55f4be...`）× 3 模型 × 3 runs：success@3 40%–55%，成功误报率 58%–77%，总成本约 $100 |
| 过程 | 观测事件 30+ 类、run_score 四维（safety/process/quality/efficiency）、registry 不可变登记 |

## 二、电梯介绍

### 30 秒版

"Synapse 是我做的本地 Code Agent Harness。模型 API 之上、IDE 之下，我关注长任务的三件事：能不能持续（上下文与记忆治理）、可不可以控制（每次工具调用 action-time 授权）、如何证明做完（外部 grader 评测链）。协议优先的架构让 6 家模型供应商和 4 类规划器即插即用，不改主循环；冻结 20 题 SWE-bench 子集上三档模型正式评测，外部 grader 消除了 58%–77% 的自报成功水分。"

### 1 分钟版

30 秒版 + 展开："具体说三个机制。上下文侧，检索是 Git-aware 的（尊重 .gitignore、AST 提符号、idf-tf 排序），组装按四区预算硬约束，超限走摘要式 compaction，历史消息超软限先 LLM 摘要再 elide。安全侧，授权发生在 action-time——同一个 shell 工具，`ls` 和 `curl | sh` 的风险完全不同，所以按 shlex token 级解析命令链、查敏感路径和重定向，SSRF 和注入扫描都在工具边界。评测侧，我不信模型嘴里的'完成'：任务跑完在干净 workspace 里 apply 补丁、跑私有测试，冻结集每题先用官方 gold patch 验证过 grader 环境才入库。"

### 3 分钟版

1 分钟版 + "为什么这是难题" + "最硬的发现"：

"为什么长任务难：上下文是持续被挤压的——历史消息每轮重发、无关文件挤占预算；状态是会断的——进程退出、中断、任务跑偏；副作用是会失控的——一个 shell 命令可能删库；'完成'是不可信的——我们三模型实测，agent 自报成功的 58%–77% 是假的，而且模型越强越自信。

架构上我用 Protocol + IoC 容器 + EventBus 三件套切分：protocols 定义 LLMProvider/Tool/Planner/Memory/Sandbox/MCP 边界，core 管生命周期，modules 放实现，adapters 是 CLI/HTTP/Library 三个入口。这个分层由 AST 架构测试锁定依赖方向，examples/extensions/ 里有 40 行的自定义 Provider 示例，新增组件零主循环改动。

最硬的发现来自评测：第一，误报率——没有外部 grader，模型表观成功率会虚高一倍以上；第二，我自己 grader 也出过事——早期环境缺依赖导致 collection error 被当成'测试未通过'，gold patch 都跑不过的环境里'verified'是有水分的，修复方式是把 gold-verified 设为任务入库门槛；第三，网关 503 中断曾被误计为模型失败，污染 16 个百分点统计，后来把 LLM 错误分成四类，5xx 计入基础设施失败。这三个发现都比分数本身有价值。"

### 5 分钟版

3 分钟版 + 时间维度数据 + 同类对比 + 边界诚实：

"补充效率维度：三档模型解题时长 117s→128s→126s（微增后持平），但分解开是两个反向变量——迭代数单调升（9.6→10.6→11.8，更强的模型做更多自我验证：主动 pip install -e .、跑官方 runtests），单迭代耗时被 API 渠道速度主导（同网关不同渠道单次调用差 28 倍）。结论是时长对比必须剥离渠道排队时间，所以我在 metrics 里加了 per-LLM-call 延迟记账。

对标市面：Claude Code 的 Task 委派、PreToolUse hooks、checkpointing 我对应做了 planner 层编排、post-event hooks（pre-tool 是明确路线）、git 快照恢复；OpenHands 的事件流思路与我的 EventBus 同源；SWE-agent 的 ACI（工具错误消息质量决定自恢复）体现在 edit 工具的 fuzzy 匹配兜底——exact 失败后 whitespace-insensitive 唯一命中 + 按行缩进对齐，找不到时错误消息直接给出最接近片段和相似度。

边界我也说清楚：默认沙箱是进程树回收不是文件系统隔离；SWE-bench 是本地适配层不冒充官方榜单；20 题样本 CI 宽，数字证明的是评测链路可信，不是能力排名。"

## 三、从多个维度理解项目

### 3.1 架构维度：模块与依赖关系

```
adapters (CLI / HTTP+SSE / Library)   ← 入口，组合根
    │
core (Container/IoC、Agent、Session、EventBus)   ← 生命周期与组装
    │
modules ├─ providers (anthropic/openai/openai_compat/deepseek/google/ollama + routing)
        ├─ planning (react / plan_execute / hierarchical / swarm + board + worktree)
        ├─ tools (read/write/edit/glob/grep/shell/git/web/browser/db/todo/skill…)
        ├─ context (retriever / partitioner / compactor / citation / budget)
        ├─ memory (session / project / user / semantic[Chroma/Qdrant])
        ├─ security (auth / sandbox×5 / injection / ssrf / audit)
        └─ mcp (stdio / streamable_http)
    │
protocols (LLMProvider/Tool/Planner/Memory/Sandbox/MCP/Events)   ← 纯接口，不依赖任何层
eval (benchmarks×4 / metrics / redteam / experiments / governance / visualize)
```

依赖方向由 `tools/check_boundaries.py` AST 检查 + `tests/test_architecture_boundaries.py` 回归锁定：protocols 谁都不依赖；modules 不得 import adapters；eval 只能依赖 core/modules/protocols。这是"零主循环扩展"的制度保障。

### 3.2 链路维度：一条 `synapse run "修 bug"` 的生命周期

1. **CLI 解析**（adapters/cli.py）：`--provider/--model` 覆盖 models.json 注册的默认；任务与 Session 绑定（TODO 清单随会话恢复）。
2. **配置合成**（config/loader.py）：内置默认 ← config.yaml（运行参数）← models.json（provider/model/key，无条件覆盖）← 环境变量。启动即校验，models.json 损坏时显式报错。
3. **容器组装**（adapters/library.py）：IoC 容器注册 LLMProvider（DeepSeek v4 走 Anthropic 协议端点的双协议路由在这里）、ActionAuthorizer、ToolRegistry、Memory、EventBus、Planner（`_build_planner` 是模式→Planner 的唯一映射点）。
4. **Agent.run**（core/agent.py）：先做上下文工程——Retriever 按 git ls-files 发现候选、idf-tf+AST 打分、CitationTracker 标记使用；Partitioner 按四区预算裁剪；超限块交 Compactor（策略 truncation/llm）。
5. **ReAct 主循环**（planning/react.py）：每轮先 `_compact_history`（超 120K 软限先 LLM 摘要再 elide），带四分类退避重试调 LLM（streaming 逐 chunk 发 LLMToken 事件）；收到 tool_calls 后逐个走授权 → 执行 → 事件；thrashing 首次触发自动回滚该文件到任务起点快照并提示换思路；token 到 80% 发警告、100% 停；代码任务成功还需跑过验证命令（completion gate），否则 PARTIAL。
6. **安全层**（security/auth.py）：每次调用前 `authorize()`——三态规则表（fnmatch）→ 按风险级分支（EXECUTE 走 shlex token 级命令链解析、`$()`/反引号触发确认、重定向查逃逸；WRITE_LOCAL 查 file_scope 与工作区边界；EXTERNAL 查 allow 开关）→ 会话级签名记忆命中则免确认。决策发 AuthDecisionMade 事件 + HMAC 审计。
7. **收尾**：ExecutionMetrics（含 llm_call_count/llm_time_ms/llm_failure）汇总成 run_score 四维；Session 原子持久化；REPL 下 checkpoint refs 已在任务起点写入 git。

### 3.3 任务维度：一个 SWE-bench 任务的执行全程

以 django__django-16877 为例（真实跑过的题）：

1. runner 从冻结 JSONL 读任务（含 repo_url=本地 mirror、base_commit、gold patch、test_patch、FAIL_TO_PASS、per-repo test_command）。
2. 临时目录 clone mirror → checkout base_commit → 把这个 repo 作为 workspace_root 构造一个全新 Synapse 实例（任务间完全隔离，无跨任务状态泄漏）。
3. agent 拿到 problem_statement 开始迭代：grep/read 定位 → edit 修改 → 主动 `pip install -e .` → `python tests/runtests.py <模块> --settings=test_sqlite` 自验 → 修正 → 完成。此过程全程 action-time 授权（eval 模式自动批准确认类）。
4. `extract_patch()` 提取工作区 diff（含新建文件）；`SWEBenchAdapter.execute()` 在干净副本里 apply 补丁 + test_patch，跑该题的 FAIL_TO_PASS 命令，returncode 判定。
5. TaskResult 记录 passed/score/verification_status/failure_kind；60 attempts 聚合出 attempt 率、task success@N、Pass@k/Pass^k、Wilson CI、repository-cluster 重采样、误报率；报告 JSON+HTML+CSV，registry 登记。
6. 入库前提（gold preflight）：该题官方 gold patch 曾在同一环境实测通过——保证"tests_passed=false"只能解释为模型修复不完整，不是环境坏。

### 3.4 数据维度：状态与产物的存储地图

| 数据 | 位置 | 生命周期 |
| --- | --- | --- |
| 会话消息 | `~/.synapse/sessions/<id>.json`（tmp→replace 原子写） | 跨进程，`--resume` 恢复 + workspace drift 校验 |
| TODO 清单 | `~/.synapse/todos/<session_id>.json` | 随会话，resume 恢复 |
| Project 记忆 | `<repo>/.synapse/memory/*.md`（YAML frontmatter） | 随仓库，团队可提交 |
| User 记忆 | `~/.synapse/memory/*.md` | 跨项目 |
| 语义记忆 | ChromaDB / Qdrant（sentence-transformers，缺依赖时 TF-IDF 降级） | 可选层 |
| checkpoint | git refs `refs/synapse/checkpoints/`（临时 index 快照，不碰暂存区） | 跨进程，/rewind 恢复 |
| 事件流 | EventBus 进程内，订阅方消费（CLI 面板/SSE/Audit） | run 级 |
| 评测报告 | `eval-results/*.json/html/csv` + registry 不可变登记 | 永久 |

## 四、面试官问题全集

### A. 架构与运行时

**A1. 为什么自己写 harness 而不用 LangChain/LangGraph？**
框架解决的是"编排图"的通用性，我的问题域不同：长任务的上下文预算治理、每次调用的授权决策、可复现评测——这些需要的是运行时控制层不是编排 DSL。LangChain 的抽象层次在我的场景反而碍事（我想精确控制每轮发什么进上下文、每个工具调用前做什么检查）。另外 harness 的核心价值在协议边界 + 安全 + 评测，这三块框架都不提供。

**A2. Protocol（typing.Protocol）为什么不用 ABC 继承？**
结构化子类型：实现类不需要继承我的基类，第三方只要"长得像"就能注册（examples/extensions/ 的 EchoProvider 没有继承任何东西）。Protocol 是声明"我需要什么"而不是"你必须是什么"，对扩展方侵入最小。ABC 的 is-a 语义适合强约束的内部层次，不适合开放扩展点。

**A3. IoC 容器具体解决什么？自己写的原因？**
解决组装与替换：LLMProvider 在容器里注册，评测 ablation 换 bypass 授权、Swarm 换 per-worker 授权、模型热切换换 provider，都是 register 一行，主循环不知道具体类型。自己写是因为需要的就 register/resolve 两 个操作，引依赖不值得（项目原则：已装依赖优先，但这是 20 行的事）。

**A4. EventBus 用了什么实现？为什么不用消息队列？**
进程内 pub/sub，按 event_type 分发，async handler。不用队列因为单进程 REPL/HTTP 是主要场景，跨进程会引入序列化与顺序问题；评测的跨进程需求由"JSON 报告 + registry"承担，那是文件即真相，不是消息。

**A5. "扩展无需改主循环"怎么证明？**
三层证明：架构测试（AST 检查依赖方向，CI 强制）；examples/extensions/ 可运行示例（自定义 Provider 40 行 + 注册 1 行，react.py diff 为零）；4 个 Planner 共享同一 Planner 协议就是历史证明——Swarm 加进来时主循环没动。

**A6. 6 家 Provider 真实的差异治理在哪？（防止被问"是不是换个 base_url"）**
三点：流式 tool-call delta 的跨家合并（OpenAI 系按 index 合并、Anthropic 的 content block 语义不同，react.py `_call_llm_stream` 统一掉）；DeepSeek v4 双协议路由（v4 模型走 Anthropic 协议端点、chat 走 OpenAI 端点，_resolve_provider 按模型名分流）；tokenizer 差异（tiktoken 不支持 DeepSeek，用估算并优先采信服务端 usage）。fallback/热切换是 routing 层（FallbackLLMProvider 带成本表）。

### B. Agent Loop 与长任务

**B1. ReAct 主循环里有哪些保护机制？（高频）**
逐轮：history compaction（软限 120K，llm 模式先摘要再 elide，失败降级）；token 预算 80% 警告/100% 停；每工具 asyncio.wait_for 超时 + 工具异常隔离成观察结果（不炸循环）；thrashing 检测（同文件 ≥3 次告警并自动回滚到起点快照、≥2 个事件停任务）；completion gate（代码任务没跑过验证命令最多 PARTIAL）；LLM 四分类重试（auth/400 快速失败，5xx/超时退避）；取消标志在迭代边界检查（Windows 有专门 SIGINT 处理）。

**B2. 为什么 thrashing 只回滚单文件不回滚整个工作区？**
首次触发时只有那个文件被证明是坏的；整区回滚会把其他文件的半成品修改一起丢掉。恢复动作本身就是副作用，越保守越好——整区恢复是用户的决定（/rewind）。另外 restore 只重置 tracked 文件、untracked 一律保留，因为无法区分"agent 建的"和"用户的"，宁可保守。

**B3. checkpoint 怎么做到不污染用户状态？**
用临时 index（GIT_INDEX_FILE 指向复制的 index）做 `add -A → write-tree → commit-tree`，快照 commit 挂在 `refs/synapse/checkpoints/`——真实暂存区和工作区零接触；挂 ref 还解决两个问题：不被 gc 回收（dangling commit 会被 prune）、跨进程可枚举恢复（resume 后 /rewind 仍可用）。

**B4. 并行工具调用怎么做的？为什么只对只读并发？**
同一轮里 READ_ONLY 且免确认的调用用 asyncio.gather 预取（_prefetch_readonly）。写/执行类保持串行：确认顺序和事件语义在并发下会乱（两个写的结果顺序、授权确认的交错），而读是无副作用的，收益/风险比完全不同。

**B5. 模型卡死在一个错误上怎么办？**
thrashing 检测 + checkpoint 回滚给一次干净重试并注入"换思路"提示；edit 工具的 fuzzy 兜底和自恢复错误消息（找不到时给最接近片段+行号，不唯一时列出全部行号）降低卡死概率；LLM 错误四分类避免在不可恢复错误上烧重试。

### C. 上下文与记忆

**C1. 四区预算是什么？为什么这样分？**
system（15%，项目规则/技能，永不裁）/core（50%，任务直接相关文件摘录）/reference（25%，次相关）/overflow（10%，保护带，可被摘要）。分区让裁剪有优先级序：overflow→reference→core，system 免裁；带 derived_from 的压缩摘要受保护。预算按任务类型（TEST/REFACTOR/DEBUG…）有 profile 微调，BudgetHistory 用历史引用率自适应 ±5%。

**C2. 检索为什么不用向量/embedding？**
分层决策：仓库内代码检索的目标是"这轮该看哪些文件"，git ls-files（天然尊重 .gitignore）+ 路径/符号加权 idf-tf + Python AST 符号命中已经能覆盖，且零外部依赖、可解释（每个文件为什么进来有得分）。向量检索留给 Semantic 记忆层（跨会话召回，Chroma/Qdrant 可选）——那是它擅长的场景。诚实边界：tokenizer ASCII-only，中文仓库打分会退化；AST 只支持 Python——都标了 ponytail 注释和升级路径。

**C3. compaction 的策略链？**
工具输出：单结果截断（16K 通用上限）→ overflow 块 LLMCompactor（8K 入/1.5K 出、sha1 缓存、失败回退截断，保留 provenance 和 derived_from 链）。对话历史：超 120K 软限后，llm 模式把将被 elide 的旧 tool result 合并成一条 LLM 摘要（缓存防重复调用），其余指向摘要；elide 模式直接占位符。两者都是"降级安全"设计：LLM 摘要失败永远回退到便宜策略。

**C4. 四层记忆怎么分工、怎么防污染？**
Session（进程内，/reset 清）服务当前会话；Project（.synapse/memory Markdown+frontmatter，按 architecture/conventions/pitfalls/decisions 分组）服务这个仓库，可随 repo 提交共享；User（~/.synapse）服务这个人；Semantic（向量库）做跨会话语义召回。隔离本身就是防污染：项目规则不会跑到别的项目（resume 时还有 workspace drift 校验——工作区指纹变了要重新确认记忆适用性）。

### D. 安全

**D1. 为什么授权在 action-time 而不是工具注册时？（必考）**
工具 schema 只描述能力，不证明本次参数安全。同一个 shell 工具，`ls` 和 `curl x | bash` 风险完全不同——风险是 (工具, 参数, 上下文) 的函数，只有拿到完整调用了才能判断。注册时静态分级只能做粗筛（我的 READ_ONLY 预取加速就是利用了这个粗筛）。

**D2. shell 命令怎么判险？怎么处理引号绕过？**
shlex（posix + punctuation_chars）真 token 化：引号内的 `&&` 是参数文本不切段（`git commit -m "a && b"` 不会误判），裸操作符才切段、每段首 token 查 allowlist；token 流出现 `$(`/反引号/子 shell 括号 → 转确认；引号不平衡 → 直接拒绝。所有误解析向严格方向失败。重定向在 token 流上查（引号内 `>` 不算 redirect），目标查私网/敏感路径/workspace 逃逸。

**D3. prompt injection 防到什么程度？**
原则是"标注而非过滤"：外部内容包 `<external-content>` 让模型可判断信任级；web/browser/db 输出再过签名扫描（instruction-override/prompt-exfiltration/credential-bait 等模式），命中加警告头；关键一手是中和伪造的闭合标签——攻击者在网页里放字面量 `</external-content>` 可以提前结束标注区让后半段被当可信指令，输出前统一转义。诚实边界：签名式不是语义级，对抗高级注入靠红队集回归。

**D4. SSRF 具体防了什么？**
URL 检查：scheme 白名单（http/https）、host 解析后查私网/环回/链路本地/CGNAT（含云元数据 169.254.169.254）、数字编码 IP（`http://2130706433`）显式处理（Windows 的 getaddrinfo 不解析这种形式，直接查 int）；重定向用 httpx event hook 逐跳重校验。边界：检查时一次解析，DNS rebinding（检查与连接间记录翻转）需要传输层 IP 固定，标注了升级路径。

**D5. 沙箱分级？**
默认 process（Windows Job Object KILL_ON_CLOSE / Unix process group）保证子进程回收——是进程围堵不是文件系统隔离，写权限由授权层管；强隔离可选 bubblewrap（--unshare-net）/seatbelt/docker（--network none）/auto。这个区分写进了 README 和评测报告的边界声明。

**D6. 权限三态和"总是允许"的记忆粒度？**
规则表是 fnmatch 通配的 ask/allow/deny，deny 在一切检查之前；"yes to all"的记忆按签名粒度——shell 记命令首 token（批准 pytest 不等于批准一切 shell）、文件工具记父目录——而不是整个工具名。硬拒绝（危险模式）不受记忆影响。

### E. 评测

**E1. 怎么证明任务真的完成了？（必考）**
三层：运行时 completion gate 看 exit code 不看文本；任务后外部 grader 在干净 workspace apply 补丁跑 FAIL_TO_PASS；正式数据集入库前 gold preflight——官方解必须先通过同一环境。三层缺一层都会漏：只有 gate 挡不住"改了但没改对"（我们 36 个失败 attempt 里 32 个是这种），只有 grader 挡不住环境性假阴性（gold 都跑不过的环境里 verified 是水分）。

**E2. 冻结 20 题正式 run 的数字和口径？**
三模型（经第三方网关的 gpt-5.4-mini/5.4/5.5）× 3 runs：success@3 = 40%/55%/40%，attempt 率 24.5%/28.3%/21.7%（Wilson CI 见报告），成功误报率 72%/77%/58%，成本 $24/$38/$38。口径限定必须带上：第三方网关（模型真实性不可验证，gpt-5.5 反常低于 5.4 但 CI 重叠、差异不显著）、本地 Windows 环境、非官方榜单。数字证明评测链路可信，不证明能力排名。

**E3. 评测体系自己出过什么 bug？（高频，考诚实度）**
三个都值得讲：①grader 环境缺依赖时 pytest collection error 也是非零，与真实失败不可分，gold patch 都跑不过——修复是 gold-verified 入库门槛；②网关 503 被记成模型失败，11 个 attempt 污染 16 个百分点——修复是 LLM 错误四分类 + infrastructure_failure_attempts；③早期文档里 parquet sha256 有笔误（前 18 位相同后文不同，基本排除篡改），重算后修正并注明。

**E4. Pass@k 和 Pass^k 是什么、为什么要分？**
Pass@k：k 次尝试至少一次通过（乐观口径，衡量可达性）；Pass^k：k 次全部通过（严格口径，衡量稳定性）。同一模型两个差距大说明不稳定（我们 5.4 的 Pass@3=55% 但 Pass^3=5%——高方差）。样本统计用 Wilson 95% CI，多题同仓库按 repository cluster 重采样避免把同仓库多题当独立证据。

**E5. 为什么按 repository cluster 重采样？**
SWE-bench 的题不独立：django 一仓 231 题，同仓题的难度高度相关。朴素 bootstrap 会低估方差（把相关性当独立性）。按仓聚类重采样（整仓进整仓出）得到的 CI 才反映真实不确定度。

**E6. 时间随模型变强怎么变？（自己挖的坑自己答）**
解题时长 117→128→126s 微增后持平，没有"先增后减"的下降支。分解：迭代数单调升（9.6→10.6→11.8，强模型自验证更多），单迭代耗时被渠道速度主导（同网关单次调用实测差 28 倍）。启示：效率对比必须剥离排队时间——所以加了 per-LLM-call 延迟记账。

### F. 同类项目对比

**F1. 和 Claude Code 比，差异和差距？**
机制对应：checkpoint↔rewind、microcompact↔auto-compact、hooks（我只做了 post-event，PreToolUse 在路线图）、权限（我的三态规则+签名记忆 vs 它的 ask/allow/deny+always allow）。差距诚实说：模型侧 subagent 委派（Task tool）我只有 planner 层编排；生态（skills 市场/MCP 服务器数量）不可比。我的差异化在评测治理——冻结集/gold preflight/误报率/registry 这套它没有，Claude Code 不解决"证明做完"。

**F2. 和 OpenHands 比？**
思路同源（事件流、可观测），它的优势在容器化执行环境和官方 SWE-bench 成绩；我的优势在本地轻量（无 Docker 依赖也能跑）、授权粒度（shlex token 级+签名记忆）和评测治理链。它的会话/事件回放比我完整（我的可视化在路线图）。

**F3. 和 Aider 比？**
Aider 是单人结对编程工具：repo map（tree-sitter）+ edit formats + git 集成，专注"改代码"单场景。Synapse 把 Aider 的场景当作 4 类规划模式之一，外加记忆/安全/评测层。它的 repo map 用 tree-sitter 多语言 AST，我的 AST 只支持 Python——这是明确差距；我的 fuzzy edit（whitespace-insensitive+缩进对齐）和它的 edit formats 解决同一问题。

**F4. SWE-agent 的 ACI 概念你怎么实践？**
ACI（Agent-Computer Interface）说工具的接口质量决定 agent 表现。我的实践：edit 失败给最接近片段+相似度+行号（不是"not found"）；不唯一给全部行号让模型自己消歧；fuzzy 兜底自动救缩进漂移；错误消息永远告诉模型"下一步能做什么"。工具错误消息是给模型看的 UI。

**F5. 为什么模型自报成功率那么不可信？**
两个机制：模型不知道"完成"的验收标准（测试它没跑过/没看到）； RLHF 让模型倾向给肯定答案。我们的数据：越强的模型误报率越高（5.4 77% > mini 72%——更流畅自信的输出+同样的验证缺失）。这也是所有"vibe coding"工具的通病，外部 grader 是唯一解。

### G. 开发过程与踩坑（故事库）

**G1. 最难的一个 bug？**
openai SDK 2.x streaming 漏 await：`create(stream=True)` 返回 coroutine，`async for` 直接炸。它藏得深是因为旧 SDK 行为不同、mock 测试替身恰好模拟旧行为——单测全绿，真实调用必炸。教训：SDK 升级后 mock 的行为假设全部失效；修复做成兼容双形态（coroutine 就 await、async iterator 直接用），且先用真实网关冒烟再上量。顺带同一批还修了 CLI `--provider` 的 argparse choices 硬编码拒绝自定义 provider——配置层支持、入口层拦截，分层不一致的典型。

**G2. Windows 兼容的坑？**
一串：git fetch --depth=1 的 commit 只在 FETCH_HEAD，本地 clone（只复制 refs 可达对象）拿不到——挂 refs/heads 分支固定；被 kill 的 git 进程留下 shallow.lock 残锁；Python 3.12 移除 distutils（老 repo 全线 LooseVersion import 失败——setuptools shim 修）、新 setuptools 移除 pkg_resources（降 <81）、django<4.1 用了被 3.13 移除的 cgi 模块（解释器级不可修，任务集按版本过滤）；NamedTemporaryFile 0 字节 index 被 git 当损坏索引。这些堆起来就是"官方 SWE-bench 用 per-task Docker"的原因——本地单 venv 有明确天花板，我把它写成了数据集口径而不是假装解决。

**G3. 并行跑两个模型的评测，怎么评估风险？**
共享可变资源只有 venv（agent 可能自主 pip install）——串行时是先后污染、并行是竞态损坏，概率低且可辨别可补跑；报告文件/临时工作区/mirror 全隔离；付费网关 2 并发无压力（实测 0 个 429/503）。收益是时长减半。但两轮必须同一代码基线（报告记录 git_commit+git_dirty，untracked 文件都算 dirty）——所以改代码必须等两轮都跑完，这个约束让我把一个修复推迟了几小时。

**G4. 评测中网站渠道挂掉的经历？**
gpt-5.4-mini 跑到 60 attempts 的最后 4 题，渠道 503 连环失败（后来整个模型下架）。当场决策：不中断主 run（49/60 数据有效）、失败 attempt 保留原始记录事后手工修正口径、设 30 分钟探测自动补跑（模型下架后取消）。事后把教训固化成代码：5xx→infrastructure_failure。数据完整性事故的标准处理就是"保真原始数据+修正口径留痕+机制化防再犯"。

**G5. 为什么想到做这个项目？**
用各类 coding agent 时的三个痛点：长任务跑着跑着上下文炸了（重发整个历史）、工具一多就不敢让它自动跑（一次 rm -rf 就完了）、说"已完成"但根本没做完。市面工具各解决一角，我想做的是把"持续/可控/可验证"作为一等公民的运行时，并且用可复现的评测证明这些机制的价值——不是又一个 wrapper。

### H. 八股与场景题（结合项目怎么答）

**H1. asyncio：为什么工具执行用 wait_for 而不是信号量？**
wait_for 管单调用超时（一个工具 120s 上限），并发度管理交给场景（只读预取 gather、写串行）——两者正交。取消传播：wait_for 超时取消内部 task，工具的清理逻辑靠 finally；用户级取消是标志位在迭代边界检查而不是 cancel 注入——选择是"边界取消"更可控（工具至少跑完或安全中断），代价是不够即时。

**H2. dataclass vs Pydantic 用在哪、为什么？**
dataclass 用于进程内数据（Message/LLMResponse/事件——热路径，零验证开销）；Pydantic 用于信任边界（config schema——YAML/JSON/models.json 进来必须校验+报可读错误）。原则：验证发生在边界，内部结构体信任已验证数据。

**H3. 原子写怎么做的？为什么需要？**
tmp 文件 + os.replace（同卷 rename 原子性）：Session/TODO/models.json/评测报告全用它。反例场景：进程在写 sessions/<id>.json 中途被杀，半截 JSON 会让 --resume 永久失败——replace 保证读者看到的要么全旧要么全新。

**H4. subprocess 安全？**
永远 list argv 不走 shell=True（git 工具的"argv exec 防注入"）；Windows 上 text+encoding="utf-8"+errors="replace"（默认 gbk 会炸 emoji/中文输出）；超时必须显式（挂死的 git fetch 拖死整个 run）；捕获输出防终端污染。

**H5. 场景：让你设计"agent 自主跑 100 个任务的批处理"，怎么做？**
直接答项目里已有的+缺的：任务级隔离（每题独立 tempdir+Synapse 实例，已有）；失败分类先行（infra/model/grader 分开统计，已有）；断点续跑（runner 级 checkpoint 目前没有——报告里有 attempt 粒度可手工恢复，机制化是改进项）；成本护栏（token 预算 100% 停，已有；美元级熔断没有，该加）；渠道健康探测+自动重试调度（有了分类基础，调度可做）。承认缺的比编造全的强。

**H6. 场景：模型输出被注入了"忽略之前指令"，你的系统哪层拦？**
四层递进：InjectionGuard 标注（外部内容包标签，模型被提示视为数据）→ 输出扫描加警告头 → 工具层防御（就算模型被骗去执行，授权层对危险命令/私网请求独立判定，不受模型意图影响）→ 审计留痕（AuthDecisionMade + HMAC）。承认没有语义级检测——对抗性场景靠红队集回归验证。

**H7. Git 八股：`git stash create`、`write-tree`、`commit-tree`、`read-tree -u` 分别干什么？**
我的 checkpoint 全用了：write-tree 把当前 index 内容写成 tree 对象；commit-tree 给 tree 加元数据生成（可悬挂的）commit；临时 GIT_INDEX_FILE 让 add -A 不碰真实暂存区；read-tree -u --reset 把 tree 硬恢复到 index+工作区（tracked 文件）。追问 refs 为什么不被 gc：只有不可达对象才被 prune，挂上 ref 就可达。

### I. 取舍与反思

**I1. 项目里最不满意的三件事？**
检索的 tokenizer ASCII-only（中文仓库退化）；HTTP server 会话内存态（与 CLI --resume 能力不对齐）；可视化缺位（事件数据都有，timeline/DAG 没渲染）。三个都在路线图，优先级低于 Aider 对照。

**I2. 做错了什么？**
早期 grader"verified"有水分却没发现——如果更早做 gold preflight，DeepSeek 那两轮"测试未通过"的结论会更干净（可能混入环境失败）。教训：验证器本身需要被验证（grader 的 grader 是 gold patch）。

**I3. 如果重做会改什么？**
事件 schema 一开始就版本化（现在加字段要考虑旧报告兼容）；测试替身少 mock SDK 边界（streaming bug 的教训——集成冒烟测试应该更早进 CI）；评测环境第一天就定 Docker per-task 路线，Windows venv 的版本天花板花掉的时间够搭 CI 容器了。

**I4. 下一步计划？**
Aider 跨 Harness 对照（同冻结集同 grader，把"有数字"变成"harness 能力证据"）；模型侧 subagent 委派工具；PreToolUse hooks。
