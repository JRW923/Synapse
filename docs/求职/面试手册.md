## 一、开口之前：速览与数字（查表区）

一段话：Synapse 是面向代码仓库长任务的本地 Code Agent 运行时。它不是把模型接口包一层的聊天机器人，而是模型和真实开发环境之间的控制层——上下文、记忆、工具授权、结果验证这四件事，都由它统一治理。

| 维度 | 数字 |
| --- | --- |
| 规模 | 115 个 Python 文件、约 2.5 万行；88 个测试文件、pytest 收集 654 个用例；支持 Python 3.11 到 3.14，Windows 是一等公民（CI 矩阵含 Windows） |
| 接入 | 6 家模型供应商（含 DeepSeek v4 双协议路由、备用切换）、4 种规划器、MCP 两种传输方式 |
| 上下文 | 四区预算加 5 套任务模板；12 万字符软上限；摘要压缩"八千进、一千五出"；检索最多阻塞 10 秒 |
| 安全 | 5 级风险决策、14 类危险命令、12 类敏感路径、5 种沙箱后端；SSRF 覆盖内网段、数字 IP、逐跳重定向 |
| 评测 | 冻结 20 题、3 档模型、每题 3 次：成功率达 40%–55%，误报率 58%–77%，总成本约一百美元 |
| 过程 | 26 类观测事件、四维运行评分、不可变的评测登记、42 处显式技术债标注 |
| 演进 | 214 次提交（2026 年 7 月中到 8 月中，约一个月），正式评测固定在代码指纹 5684c8c 上 |

## 二、电梯介绍

### 30 秒版

"Synapse 是我做的本地 Code Agent 运行时。它在模型接口之上、IDE 之下，专门管长任务的三件事：一是能不能持续跑下去——上下文和记忆的治理；二是可不可以控制——每次工具调用前现场授权；三是怎么证明做完了——外部阅卷的评测链。架构上协议优先，六家模型供应商和四类规划器都是即插即用，换组件不改主循环。我在一份冻结的二十题 SWE-bench 子集上做了三档模型的正式评测，外部阅卷挤掉了百分之五十八到七十七的自报成功水分。"

### 1 分钟版

三十秒版之后接着说："展开讲三个机制。上下文这边，检索是懂 git 的——天然跳过忽略名单，从代码里抽函数名类名参与打分，一个词越少见权重越高；组装进上下文时按四个区分配预算，实在超了就先摘要再删，历史消息太长也是先总结成摘要、再省略掉旧内容。安全这边，授权发生在每次调用的现场——同一个 shell 工具，列目录和'下载脚本直接执行'风险完全不同，所以按 shell 的规则把命令拆词、命令链逐段查白名单，还要查敏感路径和重定向，SSRF 和注入扫描都做在工具边界上。评测这边，我从不信模型嘴里的'完成'：任务跑完，在干净环境里应用它产出的补丁、跑私有测试；而且题目入库之前，我会先用官方标准答案验证阅卷环境本身是好的。"

### 3 分钟版

一分钟版之后，加"为什么这事难"和"最硬的发现"：

"为什么长任务难，我说四个点。上下文是持续被挤压的——历史每轮重发、无关文件挤占预算；状态是会断的——进程退出、任务中断、方向跑偏；副作用会失控——一条 shell 命令可能删库；'完成'是不可信的——三个模型实测下来，自报成功的百分之五十八到七十七是假的，而且模型越强越自信。

架构上我用三件套切分：协议层定义供应商、工具、规划器、记忆、沙箱这些边界；核心层管生命周期和组装；模块层放具体实现；入口有命令行、HTTP、库调用三种。这个分层有 AST 检查盯着依赖方向，CI 强制执行；仓库里有四十多行的自定义供应商示例，加新组件主循环一行不改。

最硬的发现来自评测。第一是误报率——没有外部阅卷的话，表面成功率会虚高一倍以上。第二是我自己的阅卷员也出过事——早期环境缺依赖，'收集出错'和'测试没过'表现完全一样，标准答案都跑不过的环境里，所谓'已验证'是有水分的；修复方式是把'标准答案先跑通'设为题目入库的门槛。第三是网关 503 中断曾被算成模型失败，污染了十六个百分点；后来把模型调用错误分成四类，服务器错误归到基础设施失败里。这三个发现都比分数本身值钱。"

### 5 分钟版

三分钟版之后，加效率数据、同类对比和边界：

"补充效率维度：三档模型的解题时长是小幅增加后持平，但拆开看是两个反向的变量——迭代次数单调上升，越强的模型做越多的自我验证，会主动装包、跑官方测试；而单次迭代耗时被 API 渠道速度主导，同一个网关不同渠道的单次调用能差二十八倍。所以时长对比必须把排队时间剥掉，我在指标里加了每次模型调用的延迟记账。

对标市面产品：Claude Code 的任务委派、PreToolUse 钩子、检查点机制，我这边对应做了规划器层的编排、事后事件钩子（事前拦截在路线图上）、git 快照恢复。OpenHands 的事件流思路和我的广播系统同源。SWE-agent 有个概念叫 ACI，说工具报错的质量决定 agent 的自救能力——体现在我的编辑工具上：精确匹配失败后做空白不敏感的模糊兜底，配上行号缩进对齐；实在找不到时，报错信息直接给出最接近的代码片段和相似度。

边界我也主动说清楚：默认沙箱是进程回收、不是文件系统隔离；SWE-bench 是本地适配层、不冒充官方榜单；二十题的样本置信区间很宽，数字证明的是评测链路可信，不是模型能力排名。"

### 2.1 英文 30 秒版（外企或英文面备用）

"Synapse is a local code-agent runtime I built in Python — a control layer between LLM APIs and the developer environment. It governs three things for long-horizon tasks: context continuity — git-aware retrieval, a four-zone token budget, summarization-based compaction; controllability — action-time authorization on every tool call, with shell-level command analysis and SSRF checks; and verifiability — an external-grader evaluation pipeline. On a frozen 20-task SWE-bench subset, 58 to 77 percent of agent-reported successes turned out to be false positives. The protocol-first architecture supports six providers and four planner modes with zero changes to the main loop."

## 三、简历四要点深挖（最重要的一章）

面试官最可能的入场方式就是指着简历四行里的某一行说"详细讲讲这个"。每条线都按同样的结构准备：问法变体、三十秒稿（先给结论）、两分钟稿（讲机制带故事）、追问链（由浅入深，每层都能接住）、翻车兜底。

### 要点一：长任务上下文治理

简历原文："为避免历史消息和无关文件挤占预算、仓库内容重复读取，采用 Git-aware 检索、符号提取、相关性排序、四区预算与摘要式 compaction；按配置的 Token 预算注入内容，检索故障默认最多阻塞 10s"

一句话人话：模型每轮能看的东西是有限的，我解决"该给它看什么、装不下怎么办"。

**问法变体**：
- "详细讲讲你的上下文管理是怎么做的"
- "上下文窗口不够用，你怎么处理？"
- "你怎么决定每一轮把哪些文件放进上下文？"
- "有没有做过压缩或者摘要？具体怎么做的？"

**三十秒稿**：

"长任务里上下文是被持续挤压的：历史消息每轮重发、无关文件挤占预算、同一个文件被反复读。我做了三层。第一层是检索——用 git 列候选文件，天然跳过忽略名单；按关键词稀有度打分，路径命中和函数名命中都加权；只取前八个文件的摘录。第二层是预算——上下文分四个区：系统规则永远不裁，核心材料给一半，参考资料给四分之一，留一成当缓冲。第三层是压缩——工具输出太长先截断，旧的历史先让模型总结成摘要、再省略，摘要失败就退回直接删。另外检索有十秒上限，就算它挂了也不会拖死任务。"

**两分钟稿**（在三十秒稿基础上展开）：

"为什么这事难：上下文不是一次性问题，是每一轮都在恶化。你修一个 bug，第一轮看三个文件就够了；到第十轮，历史里有九轮的对话和工具输出，再加上模型自己反复读的文件——窗口里真正有用的比例越来越低，这就是大家说的'注意力稀释'。

检索怎么挑文件：先让 git 报名单——好处是忽略名单天然生效，构建产物根本不进来；然后对每个文件打分，打分逻辑一句话能说清——一个词出现在越多文件里就越不值钱，文件里出现次数越多越值重但边际递减，路径里带关键词的加四倍权，文件里定义的函数名类名命中加两倍权。符号是用 Python 标准库的 ast 抽的，零依赖，结果有缓存，因为解析一次大概两百毫秒，不缓存每次检索都白付。

预算为什么分四区：裁剪需要优先级。系统区是规矩，裁了行为就漂，永不裁；核心区是这轮任务的案卷；参考区是备用资料；缓冲区是牺牲带，永远最先动。裁剪顺序固定：先缓冲、再参考、最后才动案卷。预算比例不是写死的——任务先分类，改测试、重构、调试各有模板；跑完还会统计'给的材料实际被引用了多少'，历史攒够三次就开始自适应浮动，一次最多百分之五。

压缩怎么做：两条线。工具输出超过一万六千字先截断——这是便宜动作；对话历史超过十二万字符，把最旧的工具结果合并成一条模型生成的摘要，最近六条工具消息永远保留。摘要为什么必要：删掉的信息永远回不来，摘要至少留住'做过什么'的骨架；摘要块还带溯源标记，在预算里受保护，不会被二次裁掉。安全设计在降级路径上：摘要调用失败，自动退回便宜的直接截断——永远不会因为'想聪明一点'把任务卡死。"

**追问链**（每层两三句，能接住就一直往下）：

1. **"打分公式具体是什么？"** 别背公式，说人话："本质是搜索引擎那套'词频乘稀有度'：一个词在越多文件出现越不值钱，在当前文件出现越多越值钱，但出现十次不比五次值钱多少；路径命中和符号命中是给代码检索加的两类强信号。"（想报细节再说：稀有度取过对数、词频做饱和、路径乘四、符号乘二，出处是 retriever.py。）
2. **"为什么不用向量检索？"** 分工不同。"这一轮该看哪些文件"是仓库内即时检索，关键词加符号已经够用，而且完全可解释——每个文件为什么进来都有得分；向量检索的主场是跨会话的记忆召回，那是我第四层记忆里可选接的。诚实说：我的分词只认英文标识符，中文仓库打分会退化；符号提取只支持 Python——这两个都是我标了债和升级路径的。
3. **"AST 只支持 Python，别的语言怎么办？"** 标准答案：换 tree-sitter 做多语言，Aider 的仓库地图就是这么干的，这是我的明确差距。别辩解。
4. **"git 挂了怎么办？"** 检索退回遍历目录；再不行整个检索有十秒上限，超时就给最小上下文（任务描述加规则），第一轮让模型自己用搜索工具找。原则：检索是增强不是依赖，增强层坏了主流程必须还活着。
5. **"摘要万一 summarise 错了怎么办？"** 三道保险：摘要块带溯源（知道它从哪几块压来的）；受预算保护但仍是"二手信息"，最近的六条工具消息永远原文保留，关键近期事实不经过摘要；摘要失败退截断，宁可丢旧的不丢对的——旧信息的价值天然低于新信息。
6. **"预算是死的还是活的？"** 活的。任务先分类套模板，再用历史引用率自适应。反馈信号来自引用追踪——进入上下文的每个块，后面有没有真的被模型用到（编辑过对应文件、引用过对应行），用过的比例回流给预算历史。
7. **"效果有数字吗？"** 诚实回答："行为回归有 654 个测试兜底，过程指标有引用率和 token 覆盖率；但'开上下文治理比不开好多少'的对照数字还没有——这正是我下一步做 Aider 对照和消融实验的动机。"别说"效果很好"。
8. **"为什么是四个区不是三个？"** 缓冲区看着多余，其实是给"摘要后仍然超限"留的软着陆——直接动参考区会一次丢太多。工程上"多一档便宜的保护带"比"边界情况硬切"稳。
9. **"12 万字符的软限怎么定的？"** 经验值加保守方向：按目标模型窗口折算后留足余量，宁可早压缩也不要撞硬墙；它是"软"的——超了才触发动作，不是拒绝执行。

**这条线的坑**：
- 别说"我做了 RAG"——我的检索不是向量检索，说错会被顺着打。
- 别背公式——被要求写公式时再写，平时说"越稀有的词越值钱"。
- 中文退化和 Python-only 两个弱点，主动说比被挖出来强。

### 要点二：分层记忆与任务恢复

简历原文："为解决跨轮事实丢失与中断重跑，采用原子持久化、/resume 续接与 Git 快照回滚；状态拆为 Session、Project、User、Semantic 四类，会话跨进程恢复，项目规则与用户偏好支持跨任务复用"

一句话人话：任务会断、事实会忘，我解决"状态放哪、断了怎么接回来、错了怎么退回去"。

**问法变体**：
- "你的记忆系统是怎么设计的？"
- "任务跑到一半断了怎么办？"
- "undo 是怎么做的？和 git 的关系？"

**三十秒稿**：

"长任务有两个躲不开的现实：进程会断、事实会忘。我把状态拆成四层：会话层的消息支持跨进程恢复；项目层的规则跟着仓库走、可以提交给团队共享；用户层记个人偏好、跨项目复用；再加一层可选的语义记忆，用向量做跨会话召回。所有写入都是原子的——先写临时文件、再一步替换正式文件，进程被杀在半路也不会留下半截数据。恢复有三件套：命令行一条指令续接会话，TODO 清单跟着会话一起恢复；每个任务开始时自动打一个 git 快照，跑偏了可以退回起点。"

**两分钟稿**（加"为什么四层"和两个故事）：

"为什么分四层而不是一个大仓库：隔离本身就是防污染。这个项目的规矩（架构约定、踩过的坑）不会漏到下一个项目里去；个人偏好不该污染团队仓库；会话里的临时状态更不该变成持久负担。每层的存储形态跟着消费者走：会话是 JSON 文件、原子写；项目记忆是带元数据头的 Markdown——因为它是给人看的，随仓库提交、代码评审能读、git 天然管版本；语义记忆是向量库，但设计成可选依赖，缺了自动降级到统计方法，再缺就纯文件——增强层永远不该让启动失败。

恢复这边有两个值得讲的故事。一个是原子写的由来：会话文件如果直接原地写，进程死在中间就是半截 JSON，恢复功能永久失效——所以我所有持久化都是'写临时文件、再原子替换'，读者要么看到全旧的、要么看到全新的，不存在中间态。

另一个是恢复时踩的协议坑：模型接口要求'工具调用'和'工具结果'必须一一配对。任务中断的时候，经常有调用发出去、结果还没回来——直接把这段历史恢复给模型，DeepSeek 会直接打回 400 错误。我的修复是：恢复时扫描全部历史，给每个缺结果的调用补一条'中断，结果已丢失'的占位结果。这个小事让我记住一个道理：协议级的不变量要显式修复，不能假设上游数据是干净的。"

**追问链**：

1. **"四层各自存什么、放哪？"** 一张嘴能报的表：会话消息放用户目录的 JSON（跨进程）；TODO 清单跟着会话走；项目记忆放仓库里的 .synapse 目录（Markdown 加元数据头，可提交）；用户记忆放用户主目录（跨项目）；语义记忆在向量库里（可选）。
2. **"恢复怎么防'接错环境'？"** 工作区漂移校验：恢复会话时先对工作区算指纹，指纹变了（比如换目录、换分支）就要求重新确认记忆还适不适用——上周的结论未必适用于今天的代码。
3. **"git 快照怎么做到不动用户状态？"** 用的是 git 底层命令三步走：把索引内容写成树对象、给树加上元数据生成一个提交对象、把这个提交挂到专用的引用下。全程用临时的索引文件，用户的暂存区和工作区零接触。挂引用还顺手解决两件事：不会被 git 垃圾回收掉（悬挂的提交会被清）；跨进程可枚举，重启之后回滚命令还能用。
4. **"为什么不用 git stash？"** stash 会动用户自己的工作区状态。快照的铁律是零副作用——我是给用户兜底的，不能顺手改用户的东西。
5. **"打转检测和快照怎么配合？"** 同一个文件被反复改三次，说明模型在这个文件上死循环了：第一次触发，把这个文件回滚到任务起点的快照，再注入一条提示'检测到反复冲突的编辑，已回滚，请换思路'——给一次干净的重试；累计第二次触发，整个任务终止、标记部分完成，把决定权交回用户。
6. **"为什么只回滚那一个文件？"** 因为只有它被证明是坏的。整区回滚会把其他文件的半成品一起丢掉——恢复动作本身也是副作用，越保守越好。大规模回滚是用户的决定，不是运行时的默认行为。
7. **"回滚时用户新建的文件怎么办？"** 一律保留。分不清是 agent 建的还是用户建的，宁可保守——恢复只重置 git 追踪的文件。
8. **"项目记忆为什么不用数据库？"** 它的消费方是模型（拼进系统区）和团队成员（要能读能改），文档型存储刚好；没有查询需求就不该上数据库。
9. **"记忆会被污染吗？怎么防？"** 层级隔离是第一道；漂移校验是第二道；语义记忆只做召回增强、不进关键路径是第三道。承认没做记忆冲突消解（两条记忆打架听谁的）——单人场景优先级不高，标了债。
10. **"HTTP 服务重启会话就丢，为什么还没修？"** 诚实：服务的会话是内存态，和命令行的恢复能力不对齐，路线图上排了持久化和恢复端点；优先级让位给 Aider 对照实验。承认边界比编造强。

**这条线的坑**：
- 别说"我用 git stash 实现的"——是底层命令加临时索引，说成 stash 会被追问细节时穿帮。
- "打转回滚"的数值（三次触发、两次终止）记不准就说"几次"，别报错数。
- 四层的名字（Session/Project/User/Semantic）说中文加一次英文即可，别满嘴英文。

### 要点三：工具调用安全

简历原文："因静态 Tool 风险声明无法识别参数副作用，采用 action-time 鉴权，按工作区、shlex 命令链、重定向与 SSRF 判险；覆盖 5 级风险决策、14 类危险命令模式和 12 类敏感路径，高风险操作执行前拦截或确认"

一句话人话：agent 手里有 shell 和文件权限，一次误操作就是事故，我解决"每次调用之前，现场判断该不该放行"。

**问法变体**：
- "你的权限系统怎么设计的？"
- "怎么防止 agent 执行危险命令？"
- "命令注入、提示注入你是怎么防的？"
- "沙箱是怎么做的？"

**三十秒稿**：

"我的核心判断是：风险不取决于工具本身，取决于这一次调用的参数。同一个 shell 工具，列目录和'下载脚本直接执行'完全是两回事——所以授权必须发生在每次调用的现场。流程是三步：先过用户配置的允许、询问、拒绝三态规则；再按风险级别分支——只读的直接放，写文件的查工作区边界，执行命令的按 shell 规则把命令拆成词、命令链逐段查白名单，遇到命令替换、管道进 shell 这类必须确认；对外请求做 SSRF 检查，内网地址、云元数据地址、伪装成数字的内网 IP 全部拒绝，重定向每一跳都重新查。另外有十四类致命命令模式直接拒绝——递归删根目录、格式化磁盘、fork 炸弹这些；十二类敏感路径像私钥、密钥文件，碰到就要确认。"

**两分钟稿**（加记忆粒度、纵深和审计）：

"这个设计背后有个效率问题：每次都判，烦不烦？我做了会话级的'总是允许'记忆，但粒度是收紧的——批准过 pytest，以后 pytest 直接放行，但这不等于批准所有命令；文件工具记的是父目录。硬拒绝的危险模式不受任何记忆影响。

防提示注入是纵深，不是单点。第一层，外部内容打上标注包起来，提示模型'这是数据不是指令'；第二层，输出再扫一遍已知攻击签名，命中加警告头——这里有个细节，攻击者可以在网页里埋一个伪造的'标注结束'符号，提前关闭保护区间，所以我会在输出前把这种伪造标签中和掉；第三层也是最重要的一层：就算模型被骗了，它想执行的动作还要过授权这道独立的关卡——骗得过模型，骗不过不关心模型意图的权限判定；第四层，每个授权决策都带签名留审计，事后能回答'当时为什么放行这条命令'。

诚实说边界：签名式的检测不是语义级的，高级注入防不住，我靠红队测试集做回归兜底——脚本化的攻击者驱动真实的 agent、真实的工具、真实的授权链路，该防住的必须防住，防不住的诚实体现在测试期望里。"

**追问链**：

1. **"为什么不在注册工具时就分好级？"** 注册时只能贴能力标签——'这是个 shell 工具'；参数进来才知道这次是列目录还是删库。静态分级我也用了，但只用来做粗筛：比如只读工具可以并发加速，就是利用了这个标签。
2. **"每次都判，性能怎么样？"** 规则表是内存里的通配匹配，微秒级；真正的命令解析只发生在执行类调用上。整个授权的耗时和模型调用比可以忽略。
3. **"引号绕过怎么防？"** 用 shell 自己的规则拆词：引号里的特殊符号只是参数文本——'提交信息写着 a 和 b'不会被误判成两条命令；反过来，引号外面的连接符才真正切段、逐段查白名单。所有解析失败一律往严的方向倒：引号不配平直接拒绝。
4. **"命令替换呢？"** 圆括号加美元符号、反引号这种，内容在解析时是未知的，一律转人工确认——不能因为外层命令在白名单就放行一个看不见内层的调用。
5. **"十四类记不全怎么办？"** 记三类就够讲：删根目录、写磁盘设备、fork 炸弹，再加'管道直接进 shell'的六个变体。设计立场比清单重要：宁可误报去确认，不可漏报放过去。
6. **"SSRF 具体防什么？"** 对外请求先查 URL：只允许网页协议；解析出来的地址查内网段、本机回环、云元数据地址——那是云上偷凭证的经典目标；还有数字写法的内网地址（把 127.0.0.1 编成一个三十多亿的十进制数），Windows 的解析器不认这种写法、常规检查会漏，我单独处理了；重定向每一跳重新查，堵'公网地址跳转到内网'。边界也说清楚：检查和连接之间域名解析理论上可以翻转（DNS rebinding），要传输层固定 IP 才能根治，标了升级路径。
7. **"沙箱到底隔离了什么？"** 分清两件事：默认后端保证子进程一定被回收——Windows 用 Job 对象、Unix 用进程组，这是进程围堵，不是文件系统隔离；文件和网络的准入由授权层管。要强隔离可以显式切 Docker、bubblewrap、seatbelt。把围堵说成隔离是最常见的夸大，我明确不这么说。
8. **"多 agent 并行写文件，怎么不打架？"** 每个 worker 有自己的文件白名单，出界在授权层硬拒——不是提示级的'请不要'，是直接拒。配套的，只读角色的工具列表在注册表层面就过滤了，模型连写工具的影子都看不到，想哄骗都没有入口。
9. **"安全这块怎么测试？"** 红队框架：攻击者是被脚本化的模型（不花真钱不连真网），但它驱动的是真实的 agent、真实的工具、真实的授权和沙箱。断言分两类：该防的攻击必须被防住；已知防不住的，测试期望里诚实写成防不住。每周 CI 自动跑。
10. **"最担心什么？"** 语义级的注入——模型被骗后用'每一步看起来都合法'的操作组合作恶，静态签名拦不住。所以纵深里我最依赖的是授权层：动作本身的危险性和模型意图无关。残余风险靠红队回归，不承诺全防。

**这条线的坑**：
- 红线：不说"防住了所有注入"、不说沙箱"完全隔离"。
- HMAC 审计被问到再展开（每个决策带签名链、可追溯），别在三十秒稿里堆。
- "数字 IP 绕过"这个细节很加分，但要能说清为什么（Windows 解析器不认、常规检查会漏），背不出数字就说"把地址编码成整数绕过检查"。

### 要点四：冻结数据与外部 grader 评测链

简历原文："针对模型自报成功不可信，以 completion gate、隔离 workspace 与重复统计；SWE-bench 冻结 20 题 gold 子集三模型×3 评测，success@3 达 40%-55%、误报率 58%-77%"

一句话人话：模型说"做完了"不可信，我解决"怎么证明真的做完了、数字怎么算才可信"。

**问法变体**：
- "误报率 58% 到 77% 这么高，怎么得出的？"
- "你怎么判断一个任务真的完成了？"
- "为什么不直接报个成功率？"
- "讲讲你的评测体系"

**三十秒稿**：

"起点是一个刺眼的发现：模型自报的成功里，百分之五十八到七十七是假的，而且模型越强越自信、假得越流畅。所以完成判定我做了三层：运行时那层看验证命令的退出码，不看模型的文字；任务跑完后，由独立的阅卷员在干净环境里应用补丁、跑私有测试；再往前，题目入库之前，先用官方标准答案验证阅卷环境本身是好的。题目集是冻结的——二十道题连同答案锁死、算好指纹，跑完不能改；每题跑三次、三档模型，所有比例都带置信区间。结论一句话：这套数字证明的是评测链路可信，不是模型排名。"

**两分钟稿**（加三个自踩的坑）：

"三层为什么缺一不可，我用自己的事故证明过。只有第一层（运行时看退出码），挡不住'改了但没改对'——我们六十次失败尝试里，三十二次都是模型改了代码、也自称验证过，但补丁就是不对。只有第二层（外部阅卷），挡不住环境性冤案——早期我的阅卷环境缺依赖，'收集出错'和'测试没过'在返回码上长得一模一样，连官方标准答案都跑不过。那种环境里，所谓'已验证'是有水分的。所以我加了第三层：每道题入库前，标准答案必须先在这套环境里真的通过——保证'阅卷说不过'只能解释为模型没修好，不是环境坏了。说白了，验证器本身也需要被验证。

统计口径也踩过坑。有一次渠道连续 503，十一次尝试被我算成了'模型失败'，污染了十六个百分点——修复是把模型调用错误分成四类，服务器错误归入基础设施失败单列。还有一次，文档里数据集指纹抄错了几位，重算后修正并注明。这三件事（阅卷环境、网关故障、指纹笔误）的修复都固化成了机制：入库门槛、错误分类、不可变登记。

最后是冻结和预注册：题目和答案锁死、算哈希、登记进只追加不修改的注册表；实验前先写下主指标和样本量。这些防的不是模型，是'做评测的人自己'——防止事后挑好看的数字。"

**追问链**：

1. **"误报率怎么定义的？"** 分母是"agent 自认为成功"的尝试数，分子是其中外部阅卷判失败的次数。三档分别是 61.9%（有效口径 72.2%）、76.9%、58.3%。mini 有两套口径是因为它有十一次网关 503，剔除后分母变了。
2. **"为什么越强的模型误报越多？"**（中档最高）输出更流畅自信，但它没见过验收标准这个根本问题没变；训练又偏爱肯定答案。流畅不等于正确，这正是'氛围编程'类工具的通病。
3. **"success@3、Pass@k、Pass^k 绕晕了，说清楚。"** 一道题给三次机会至少成一次——这是任务视角的 success@3；Pass@k 是样本视角的估计；我额外算了 Pass^k——三次全成的比例，衡量稳定性。中档模型给三次机会能成 55%，但三次全成只有 5%：偶尔做对不代表稳定做对，这对生产使用是关键区别。
4. **"为什么只有 20 题、3 次？"** 成本约束下的设计：一百八十次尝试、约一百美元，每题还都要先跑通标准答案。样本小所以一切结论带威尔逊区间，而且明确说这样本量不支持能力排名——把口径边界说清楚，本身就是我想展示的评测素养。
5. **"为什么用威尔逊区间？"** 二十题、比例又常靠近零或一，正态近似会算出不靠谱甚至越界的区间；威尔逊在小样本下覆盖率好。配对比较另有麦克尼马检验——只看两边结果不一致的对，一致的对不提供区分信息。
6. **"同仓库的多道题怎么办？"** 我的二十题里 django 九道、sympy 十道——同仓题难度高度相关，当成独立样本会虚假地缩小区间。置信区间按'整仓进整仓出'的聚类重采样算。
7. **"三档模型的结果怎么解读？"** 40%、55%、40%。反常识的是最高档没更高——但置信区间大幅重叠，差异不显著，不能解读成'5.5 比 5.4 差'。第三方网关加小样本，这就是口径边界：数字证明链路，不证明排名。
8. **"成本怎么记的账？"** token 数优先取服务商回执（覆盖率百分之百），乘报告里声明的单价，可复算——mini 档二十四块三毛一分能精确对上账；网关标价是另一套口径，不混用。
9. **"阅卷员自己怎么校准？"** 六个标准案例：正确、接近正确、删测试作弊、硬编码通过、空补丁、越界改动——每个案例期望的判定是预写的，阅卷员对这六类的判定回归通过，才信它对真实尝试的判定。
10. **"为什么不用官方 SWE-bench 环境？"** 用官方跑过标准答案冒烟（一道题判定通过，专门验证阅卷可信）。自建适配层是因为官方假设每题一个 Docker，我在 Windows 本地单环境跑——这个天花板写进了数据集口径；而且我的目标是评测自己的运行时，需要任务级隔离地把 agent 嵌进跑分流程。报告里明确标了'外部适配，非官方成绩'。
11. **"和业界评测方法对得上吗？"** 对得上：有篇论文（arXiv 2507.02825，Kapoor、Liang 这些人）系统梳理过 agent 基准的坑——SWE-bench Verified 存在测试不足、有的基准把空回复算成功，相对误差最高百分之百。我踩的坑和他们的清单高度重合：标准答案入库对应'任务设置可验证'、误报率对应'奖励不被钻空子'、冻结预注册对应可复现。区别是他们做方法论，我在工程里落了同一条链。
12. **"数字难看，价值在哪？"** 价值在三件事：链路可信（一百八十次尝试全部经过外部验证、阅卷零故障）、误报率第一次被量化（行业里很少有人报这个数）、口径完整（置信区间、成本、代码指纹全记录）。分数难看的是模型，不是我。

**这条线的坑**：
- 红线：不说"Harness 或模型能力提升百分之多少"；不把本地成绩说成官方榜单分数；不说 55% 对 40% 是能力差异。
- mini 的误报率能报双口径（原始 61.9%、有效 72.2%）——被追问口径时这是加分项，含糊其辞是减分项。
- 三个自踩坑的修复措施要和坑对得上（环境坑对应入库门槛、网关坑对应错误分类、指纹坑对应重算注明）。

### 4.1 架构维度：分层与依赖

    |

    |

依赖方向用 AST 检查加回归测试锁死，规则一张嘴能报：接口层谁都不依赖；模块层不许反向碰入口层和配置层；评测层不碰入口层；入口层是组合根、谁都能用。另外还有一份第三方库白名单，名单外的依赖直接报错——防依赖悄悄膨胀。"扩展不改主循环"不是口号，是这条被 CI 强制的规则加一个四十多行的示例（自定义供应商示例总共四十六行，加新组件时主循环的改动是零行）。

### 4.2 链路维度：一条"修 bug"命令的完整生命周期

1. 命令行解析：参数覆盖配置文件里注册的默认模型；任务和会话绑定。
2. 配置合成：内置默认，被项目配置覆盖，再被模型配置覆盖，最后环境变量优先；启动就校验，配置文件坏了直接报错。
3. 容器组装：登记供应商（DeepSeek v4 的双协议路由在这里做——v4 系模型走 Anthropic 协议端点、chat 走 OpenAI 端点）、授权器、工具注册表、记忆、事件总线、规划器。
4. Agent 启动先做上下文工程：检索挑文件、打分、标记引用；分区器按预算裁剪；超限的块交压缩器。
5. 主循环：每轮先检查历史要不要压缩；调模型（流式，逐块发事件）；拿到工具调用逐个走授权、执行、发事件；打转检测随时待命；token 到八成警告、用满就停；代码任务最后必须跑过验证命令才算成功。
6. 授权层：每次调用现场判——三态规则先走，再按风险级别分支，会话记忆命中就免确认；决策发事件加签名审计。
7. 收尾：指标汇总成四维评分；会话原子落盘；任务起点的 git 快照早就打好了。

### 4.3 任务维度：一道评测题的全程（以一道 django 真题为例）

1. 跑分器从冻结题库里读题：仓库地址（本地镜像）、起始提交、标准答案、测试补丁、必须从失败变通过的测试名单、这个仓库专用的测试命令。
2. 临时目录克隆镜像、切到起始提交，把它作为一个全新 agent 实例的工作区——任务之间完全隔离，没有跨任务状态泄漏。
3. agent 拿到题目描述开始迭代：搜索定位、编辑修改、主动装包、跑官方测试自验、修正、完成。全程走真实授权（评测模式下确认类自动批准）。
4. 跑完后从工作区提取补丁（含新建文件）；阅卷器在一份干净副本里应用补丁和测试补丁，跑"必须通过"的测试，按返回码判定。
5. 结果聚合：单次通过率、任务成功率、Pass@k 和 Pass^k、置信区间、按仓聚类的重采样、误报率；产出机器可读报告加可视化页面，登记进注册表。
6. 而这道题能进题库的前提是：官方标准答案曾在这套环境里实测通过。

### 4.5 演进维度：一个月怎么长出来的（214 次提交）

被问"这项目怎么发展出来的"，按七段讲，每段都有提交记录佐证：

3. 然后上深度能力：上下文工程、流式、过程质量闭环、蜂群多 agent、红队框架、运行时评分；对照一份自己列的二十项审计清单逐项补。

6. 评测治理与外部验证：冻结清单、预注册、阅卷校准、结果登记；官方 SWE-bench 跑通标准答案冒烟。

## 五、代码细节追问库（防"真是你写的吗"）

面试官往实现层钻时，能报出机制和取舍比背概念有说服力。每条按"追问、要点"准备，出处只在需要背书时提。

### 5.1 编辑工具

- **模糊匹配到底怎么做的？** 精确匹配先数出现次数：零次进入模糊救援——把文件每一行和新内容的每一行都去掉首尾空白后做滑窗比较，窗口长度等于新内容行数，唯一命中才算数。注意：匹配是去空白后的精确相等，不是相似度阈值；相似度（标准库 difflib）只用在失败时的提示——"你是不是想改第 N 行附近，相似度零点八五"。
- **缩进漂移怎么救？** 命中后逐行算缩进差（文件行前导空格减新内容行前导空格），把替换文本逐行平移——解决模型复述代码片段时丢嵌套缩进的问题。右移补空格、左移只在确有富余时执行，空行不动。
- **多个位置都匹配呢？** 直接报错，列出前八个行号，要求补上下文——拒绝猜。模糊匹配多个命中同样拒绝。
- **Windows 的坑？** 写回时禁用换行符自动转换，保留原文件的换行风格——否则整文件被重写，diff 全红。

### 5.2 供应商层

- **流式的工具调用增量怎么合并？** 按序号分槽累积：标识和名字有值就覆盖；参数有的是字典（谷歌直接给）、有的是分片字符串（OpenAI 系要拼），流结束后统一解析成 JSON，解析失败容错成空对象。
- **流式的备用切换有什么坑？** 关键是一个标志位：一旦已经向外吐过任何内容块，后续出错就直接抛、不再切下一家——否则用户会看到两份拼接的半截回复。本质是"非幂等的副作用发生之后不可重试"。
- **token 计数怎么做的？** 双源对账：服务商给了权威数字就采信；没有就用本地分词器对每个增量累计估算，让界面上计数平滑跳动，最后以真实总数收口。
- **DeepSeek 双协议具体是什么？** v4 系模型走它的 Anthropic 协议端点、chat 走 OpenAI 兼容端点，按模型名分流；Anthropic 端点不支持显式缓存标记，要强制关掉。
- **分词器不认识 DeepSeek 怎么办？** 用近似分词表估、未知模型回退通用表，并优先采信服务端回执——估算只影响过程显示，不影响账单口径。

### 5.3 主循环与恢复

- **修复会话是什么？** 恢复时给所有缺结果的工具调用补一条"中断，结果已丢失"的占位结果——不补的话模型接口直接 400。这是"协议不变量显式修复"的小典型。
- **历史压缩怎么挑牺牲品？** 只挑超过两百字且没被打标的块，最近六条工具消息永远不动；先摘要后省略，摘要失败退回直接省略。
- **只读工具为什么可以并发？** 同一轮里只读且免确认的调用并发预取；写和执行类保持串行——确认的顺序和事件语义在并发下会乱。读是无副作用的，风险收益比完全不同。

### 5.4 MCP

- **踩过最深的坑？** 官方 SDK 的会话对象必须作为异步上下文管理器进入才会启动后台消息泵——裸构造它，初始化就无限挂起，没有任何报错。定位靠读 SDK 源码看它什么时候起后台任务。附带发现：连接绑定事件循环，宿主每次新建循环后整组连接失效，做了检测加自动重连。
- **两种传输都实现了什么？** 子进程方式和流式 HTTP 方式；第三方工具包装成统一命名，默认标最高风险级进授权体系。

### 5.5 蜂群多 agent

- **角色怎么隔离？** 默认两个编码角色加一个评审角色：编码角色各有不相交的文件写白名单，出界在授权层硬拒；评审角色的工具列表在注册表层就过滤——模型连写工具的入口都看不到。
- **评审判定怎么防误伤？** 用显式的中英短语判"通过、驳回、要改"，两个信号一致或完全没有信号时默认"要改"不放行；不匹配裸的"失败"字样——旧版本会被"没有测试失败"这种话误伤成驳回。
- **为什么另有一个串行的分层规划器？** 分层的用会话分叉串行执行子任务（注释里写明：并行会放大错误），蜂群是刻意反过来的并行版（多工人加评审循环）。两个规划器就是"串行正确性对并行吞吐"的一组对照实验。

### 5.6 核心层

- **容器多大？** 五十三行：登记单例、登记工厂、取用，外加泛型降级。需要的就是这几个操作，引依赖不值得。
- **广播系统的细节？** 发布用并发分发，单个订阅者抛异常只记日志不传播——观测不能杀死主流程；每个事件自动带运行标识和因果链（父事件滚动）；二十六类事件不是一开始设计好的，是随能力长出来的，共同点是命令行面板、HTTP 推送、审计、评测报告消费同一个事件源。
- **Agent 本体有多少循环？** 零——它只做五步（建上下文、打信任标注、委托规划器、回收引用统计、持久化），循环全在规划器里。编排和策略分离的直接体现。

## 六、评测体系深讲（重点章节）

> 简历第四条全押在评测上，这章是它的完整弹药库：每套评测是什么、每个数字说明什么、业界怎么做、我还差什么。

### 6.1 设计哲学：为什么是七套评测而不是一套

单一基准回答不了四个正交问题：**功能对不对、稳不稳定、花多少资源、过程合不合规**。所以评测是分层的，下层是上层的地基：

| 层 | 评测 | 回答的问题 | 频率 |
| --- | --- | --- | --- |
| 契约层 | terminal_smoke、repo_pytest | 评测链路本身坏没坏 | 每次 CI |
| 功能层 | swebench / terminal_bench 适配 | 任务功能正确性 | 显式触发（花钱） |
| 对抗层 | 红队注入种子集 | 护栏有没有被绕过 | 每周 CI |
| 因果层 | experiment A/B | 某个机制有没有因果贡献 | 按需 |
| 治理层 | 冻结/预注册/登记 | 结论是否可审计可复现 | 每次正式 run |
| 观测层 | 运行时四维评分 + 过程质量 | 每次运行的过程诊断 | 每次运行 |

最关键的设计决策：**契约层不花钱、天天跑——评测系统自己的回归测试**。这是教训换来的：阅卷环境坏掉时（缺依赖导致收集阶段就报错），上层所有数字都是错的。评测的评测，比评测本身更底层。

### 6.2 逐套深讲：是什么、怎么跑、结果、意义

**① repo_pytest——组装后的行为契约。** 临时 git 仓库、agent 真实修改、pytest 阅卷。和单元测试的区别：单测验证零件，它验证组装后的完整行为（agent→工具→修改→测试→判分→报告）。意义：我做大改造（shlex 命令解析、检查点接入）之后跑它，证明功能语义没被重构破坏。这是最便宜也最常用的"改动是否伤到端到端"检查。

**② terminal_smoke——离线评测契约。** 纯离线终端夹具，验证文件状态和命令结果。意义：无网络无密钥的环境（CI、新机器）也能验证报告契约、统计口径、阅卷行为——每晚的守护者：它不过，上层一切暂停。

**③ terminal_bench 适配——外部任务集入口。** 兼容常见 JSON/JSONL 任务字段、隔离工作区、命令阅卷。意义：接入任意外部终端任务集的标准接口。和 smoke 的分工：smoke 是自造夹具（测自己），bench 是外部数据（测能力）。当前没有可信任务数据，刻意不凑数。

**④ swebench 本地适配——功能正确性主战场。** 流程：冻结题库（每题带起始提交、标准答案、测试补丁、必须通过的测试名单、该仓库专用测试命令）→ 隔离克隆 → agent 修题 → 提取补丁 → 干净副本应用并跑私有测试 → 返回码判分。正式跑分有三道质量闸门：**分层随机抽样**（按仓库配额、种子固定、选择过程可复现）；**标准答案入库验证**（官方解在本环境实测通过才入库——首轮二十题淘汰五题、按版本约束补选、最终二十题全过，淘汰原因留痕：老版本 django 依赖的解释器级不兼容修不了）；**失败分类**（网关 5xx 算基础设施失败，不污染模型统计）。结果：三档模型各二十题三次，成功率 40%/55%/40%，自报水分 72%/77%/58%，总花费约一百美元。**这套数字的意义不是排名，是证明评测链路能产出可信结论**——二十题置信区间宽、第三方网关模型真实性存疑，这两个限定我主动写在报告里，不等人来戳。

**⑤ 红队种子集——对抗回归。** 确定性注入种子（近似正确、删测试、硬编码、空实现、越界修改等攻击模式）。意义：护栏回归而非能力分——每周验证注入扫描和授权拦截没被日常重构悄悄破坏。实证：正式跑分中注入扫描触发 253 次、危险命令拦下 16 次、零沙箱违规。边界诚实：确定性种子防退化不防新攻击，语义级对抗要真实模型红队（路线图）。

**⑥ experiment A/B——因果归因。** 同轮随机交错、配对自助法、随机化检验、多指标独立方向加护栏。意义："某个机制有没有用"必须受控比较——模型输出本身高方差，不配对的两次总分对比全是噪声。HTTP 入口只放行受限配置差异（拒绝密钥、工作区、沙箱注入），防止网络请求变成宿主执行。待跑的高价值实验：历史压缩的"丢弃式 vs 摘要式"配对——摘要开销换成功率的量化。

**⑦ 治理链——证据治理。** 冻结（数据集指纹）、预注册（跑之前钉死主指标、样本量、停止规则）、登记（只增不改的注册表）、校验、趋势。意义：防"跑十次挑最好的一次发出去"。预注册约束的是未来的自己——三个正式 run 都登记在册，同系列可比。**这是整个体系里最反人性也最值钱的部分**：它不产出分数，它产出"分数可信"。

**⑧ 运行时四维评分——过程观测。** 四维（安全/过程/质量/效率）加过程质量信号（检索命中、根因证据、测试留存）。意义：功能分之外的诊断维度，也是**自报水分的来源**——agent 自报成功和外部判分的差值就在这张表里，让"模型说做完了"从口号变成可度量的列。

### 6.3 每个数字的意义与价值（读表指南）

| 数字 | 回答什么 | 我们的读数怎么解 |
| --- | --- | --- |
| 任务成功率（success@3） | 可达性：三次里至少一次过 | 三档模型 40%/55%/40%——都"够得着"部分题 |
| 单次通过率 | 单次稳定性 | 21%–28%——单次低，重复才可见 |
| Pass^k（全过率） | 一致性 | 某档模型 Pass@3=55% 但三次全过只有 5%——"偶尔对"不等于"稳定对"，高方差 |
| 置信区间 | 样本量的诚实代价 | 二十题的区间宽到横跨三十多个点，这就是不排名的原因 |
| 自报水分率 | 没有外部阅卷会怎样 | **全体系最有价值的单一数字**：58%–77% 的自报成功是假的；且模型越强越自信（最高那档反而水分最大） |
| 基础设施失败 | 结论可信度的守门员 | 一轮里十一个网关 503 曾污染十六个百分点的统计——修复后自动归类 |
| 时间分解 | 效率归因 | 时长 = 迭代数 × 单迭代；渠道间单次调用差 28 倍是最大混淆项，按调用记账已加上 |
| 每次成功成本 | 效率定价 | 按成功计费（两到三美元一次成功）比按运行计费公平——失败的运行也烧钱 |

### 6.4 业界怎么做 agent 评测（2026 对照）

**基准版图**：SWE-bench Verified 仍是代码修复的黄金标准，头部已达 85%–94%（饱和中，社区转向更难的切分和多模态变体）；Terminal-Bench 2.0（约 89 个终端任务）覆盖工具使用；tau-bench 类多轮工具任务头部才 50%–70%——**交互式长程任务远未解决**；GAIA（通用助理）、OSWorld / WebArena（图形界面）各占一角。

**方法论共识**：外部阅卷/私有测试判分、每任务独立容器、防污染（时间切分、金丝雀字符串）、阅卷口径标准化——SWE-bench 官方现在同时报告标准化 harness 口径，正是因为 harness 差异会污染模型排名（和我"跨 harness 对照必须同模型同任务同阅卷"是同一个洞察）。

**我的体系和业界的映射**：外部阅卷 ✓（三层：完成门槛/阅卷/标准答案入库）、冻结与清单 ✓、CI 分层 ✓、自报水分量化 ✓（业界报告普遍只给解决率，自报水分少有人度量——这是我的差异点）、基础设施失败分类 ✓（很多公开报告对渠道中断只字不提）。防污染 △（模板变异是弱手段）。环境隔离 ✗（单环境 vs 容器）。跨 harness 对照 ✗（未完成）。

### 6.5 差距清单（按硬度分级，每条带升级路径）

**硬差距**（影响结论强度）：
1. **环境隔离**：本地单一环境 vs 业界每任务容器——版本天花板三连坑（distutils、pkg_resources、被移除的 cgi 模块）的根源。升级：官方镜像加容器编排，口径切官方跑分器。
2. **样本量与统计力**：二十题 vs 官方五百题——区间宽到无法排名。升级：预算允许时全量（现价约一千美元一模型三轮）。
3. **跨 harness 对照未完成**：同冻结题库和阅卷下对比另一个 harness——这是"harness 有没有用"的前提，已列最高优先级。
4. **防污染弱**：模板变异（同义替换加指令重排）只防表面记忆。升级：按任务创建时间过滤训练截止后的题。

**中差距**（覆盖面）：
5. 长程多轮交互任务（tau-bench 类）未接入——当前都是单轮"读题修题"。
6. 无人评维度（代码风格可接受度、方案合理性）。
7. 效率对比标准化：对照 harness 不吐用量就进不了效率列（业界通病，各家口径不一）。
8. 注入检测是签名式不是语义级。

面试话术："我的评测强在治理链和可信度——标准答案入库、自报水分度量、基础设施失败分类；弱在规模和覆盖。下一步优先补跨 harness 对照，因为它直接决定'harness 有没有用'这个问题能不能回答。"

## 七、问题全集

> C、D、E 三组的主体已并入第三章对应要点的追问链，这里只留补充题。

### A. 架构与运行时

**A1. 为什么自己写而不用 LangChain 这类框架？**
框架解决的是"编排图"的通用性，我的问题域不同：长任务的上下文预算、每次调用的授权、可复现的评测——这些要的是运行时控制层，不是编排 DSL。而且框架的抽象层次在我的场景反而碍事：我要精确控制每轮发什么进上下文、每个工具调用前查什么。核心价值在协议边界、安全、评测这三块，框架都不提供。

**A2. 接口为什么用 Protocol 不用基类继承？**
结构化子类型：实现类不需要继承我任何东西，只要"长得像"就能注册——仓库里的示例供应商没继承任何类。Protocol 是声明"我需要什么"而不是"你必须是什么"，对扩展方侵入最小。

**A3. 容器具体解决什么？为什么自己写？**
解决组装与替换：评测里换绕过授权的配置、蜂群里换按角色的授权、模型热切换，都是登记一行的事，主循环不知道具体类型。自己写是因为需要的就登记和取用两个操作——这是二十行的事，引依赖不值得。

**A4. 事件总线为什么不用消息队列？**
单进程的交互式场景是主场景，引队列会带来序列化和顺序问题。跨进程的需求由"报告文件加注册表"承担——文件即真相。

**A5. "扩展不改主循环"怎么证明？**
三层：架构测试在 CI 里强制依赖方向；仓库里有四十六行的示例供应商，加它时主循环改动为零，而且有测试真的执行这些示例；四个规划器共享同一个接口本身就是历史证明——蜂群加进来的时候主循环没动。

**A6. 六家供应商，真实的差异治理在哪？（防"不就是换个地址"）**
三点：流式工具调用增量的合并规则各家不同，我在主循环里统一掉了；DeepSeek v4 是双协议路由，按模型名分流到两种端点；分词器差异，用近似加采信服务端解决。备用切换是路由层的事，关键设计是"流式已经吐过内容就不切换"。

**A7. 并发请求下安全吗？**
诚实说：规划器的运行时替换是实例级的，多请求共享一个实例时不安全——显式标注过的边界，当前场景（单用户交互、每任务独立实例）不触发。HTTP 会话持久化在路线图里，会一并处理。

**A8. 事件怎么设计的？**
不是一开始设计好的，是随能力长出来的：工具、授权、上下文、规划、蜂群、恢复各有各的事件。设计纪律只有一条：命令行面板、HTTP 推送、审计、评测报告消费同一个事件源，没有第二条观测通道。

**A9. 命令行入口三千行，失控了吗？**
承认是最大单体，但方向是对的：它只做入口加渲染，渲染层已经拆出去了，业务逻辑都在模块层。组合根本来就厚。继续拆在待办里，不是风险。

**A10. 评测层为什么不许碰入口层？**
评测要构造完整实例，但绝不能依赖入口——否则命令行改动会破坏评测可复现性。正式评测还记录代码指纹，保证可追溯。

### B. 主循环与长任务

**B1. 主循环里有哪些保命机制？（高频）**
一口气数八道：历史太长先压缩；token 有硬预算（八成警告、用满就停）；每个工具有超时，工具抛异常只当一次观察结果喂回模型、不炸循环；打转检测（同文件改三次自动回滚加提醒，两次打转终止任务）；完成有门槛（没跑过验证命令最多算部分完成）；模型调用失败分四类（认证和参数错误立刻放弃，服务器错误和网络超时才退避重试）；取消在安全点检查、不拦腰截断工具；Windows 下有专门的 Ctrl+C 处理。

**B2. 为什么取消用标志位不用强制取消？**
边界取消更可控：工具至少跑完或安全中断，清理逻辑有保障。强制取消会在任意等待点抛异常，半途而废的状态更难收拾。代价是不够即时——这是标注过的取舍。

**B3. 完成门槛的判定细节？**
看验证命令的退出码，不看模型文字。代码类任务收尾时没有"跑过验证"的证据就降级部分完成——这是运行时第一道，后面还有外部阅卷和入库验证两道。

**B4. 模型卡死在一个错误上怎么办？**
打转检测加快照回滚给一次干净重试，附一条"换思路"的提示；编辑工具的模糊兜底和自愈式报错（找不到时给最接近片段加行号，多处命中时列全行号）从源头降低卡死概率；错误四分类避免在不可恢复的错误上烧重试。

**B5. 中断恢复后上下文怎么接上？**
三层：会话原子持久化加续接命令（带漂移校验）；给缺结果的工具调用补占位结果，保住协议配对不变量；TODO 清单随会话恢复，长任务的计划状态不丢。

### C. 上下文补充题（主体见要点一）

**C1. 引用追踪是干什么的？**
记录每个进上下文的块有没有真的被模型用上。两个消费者：预算自适应用它的历史引用率做浮动依据；运行评分的效率维度用它算 token 有效率。让"预算该给多少"从拍脑袋变成有反馈信号。

**C2. 检索结果有噪声文件混进来怎么办？**
预算分区本身就是降噪：核心区只放高分文件，低分的进参考区、随时可弃；摘录带行号，模型能验证来源。真正的过滤靠第二轮自净——模型读完发现无关，引用率统计会降它的权重。

### D. 安全补充题（主体见要点三）

**D1. 路径前缀检查出过什么 bug？**
数据库工具早期用字符串前缀判断工作区，"ws-evil"能绕过"ws"——换成路径语义的相对定位后才算堵死。教训：字符串匹配类逻辑的对抗面比想象大。

**D2. 授权决策的审计具体记什么？**
每次决策三要素：结论（放行、确认、拒绝）、理由（命中哪条规则或模式）、签名（这命令长什么样）。带签名链防篡改，事后能回答"当时为什么放行"。

### E. 评测补充题（主体见要点四）

**E1. 时间随模型变强怎么变？（自己挖的坑自己答）**
解题时长小幅增加后持平，没有传说中"先增后减"。拆开是两个反向变量：迭代次数单调上升（强模型做更多自我验证），单次迭代耗时被渠道速度主导（同网关不同渠道差二十八倍）。所以效率对比必须剥离排队时间——加了每次调用的延迟记账。

**E2. 评测方法学和业界对得上吗？**
对得上，详见要点四追问第 11 层（arXiv 2507.02825）。可以补一句：他们做方法论，我是单人在工程里落地了同一条链。

**E3. 和榜单分数怎么比？**
不能直接比，但给语境：榜单头部（2026 年 8 月快照）是 Claude 4.5 Opus 官方环境 79%、一个一百行代码的极简 harness 拿 65%。我的 40%–55% 出自本地 Windows、第三方网关、自建阅卷、二十题——口径完全不同。任何数字离开口径都没有意义，这正是我想展示的素养。

### F. 同类项目与行业对比

**F1. 和 Claude Code 比，差异和差距？**
机制对应得上：检查点对回滚、自动压缩对摘要压缩、钩子（它有事前拦截，我只有事后通知、事前在路线图）。差距诚实说：它的子代理有独立上下文窗口、内置探索和规划角色、后台并发、输出扫描——我只有规划器层的编排，模型侧的委派工具在路线图；生态更没法比。我的差异化在评测治理：冻结、入库验证、误报率、登记这套它没有——Claude Code 不解决"证明做完了"。

**F2. 和 OpenHands 比？**
思路同源（事件流、可观测）。它的优势在容器化执行环境和官方成绩；我的优势在本地轻量（不装 Docker 也能跑）、授权粒度和评测治理链。它的会话回放比我完整。

**F3. 和 Aider 比？**
Aider 是单人结对编程工具：仓库地图（tree-sitter 多语言）加编辑格式加 git 集成，专注改代码一个场景。Synapse 把这个场景当作四种规划模式之一，外面还有记忆、安全、评测层。它的仓库地图用 tree-sitter 加图排序——我的符号提取只支持 Python，这是明确差距；我的模糊编辑和它的编辑格式解决同一个问题。Aider 是我下一步的对照实验对象：同题、同模型、同阅卷做配对比较。

**F4. SWE-agent 的 ACI 概念你怎么实践？**
它说工具接口的质量决定 agent 表现。我的实践：编辑失败给最接近片段加相似度加行号，不是一句"没找到"；多处命中列全行号让模型自己消歧；报错永远告诉模型下一步能做什么——工具报错就是给模型看的界面。有意思的是它的后继项目反向验证了同一件事：一百行的极简接口也能拿 65%，说明脚手架不是越多越好；我的复杂度花在治理上，不是花在冲分上。

**F5. 和 Cursor 这类 IDE 内置 agent 比？**
场景不同：它的主循环在 IDE 里，强在补全、索引、多文件编辑的产品化；弱在自主长任务的治理——上下文策略、授权、可验证完成都不是它的卖点。我是无界面的运行时，三个入口，可以被 IDE 包（适配目录就是这个意图）而不是去包 IDE。差距：它有生产级的常驻代码索引，我的检索每轮即时算——各有取舍，我的零索引成本、可解释。

**F6. MCP 生态你怎么看？为什么接？**
它是事实上的工具协议标准：开放标准、两种传输、工具、资源、提示三类原语、能力协商、授权。接入理由很实际：生态复用——浏览器、数据库、设计工具都有现成的服务器，不用每个自己写；安全侧把第三方工具统一标最高风险级进我的授权体系。我的判断：MCP 解决"工具发现和调用的标准化"，不解决"该不该调用"——后者永远是运行时的责任。

**F7. Anthropic 那篇上下文工程的文章和你的实践对照？**
概念全对得上：他们说的注意力预算对四区预算；"最小高信号集合"对打分取前八；即时检索对预计算的混合，对系统提示前置加模型自己搜的分层；压缩保留最近访问文件，对保留最近六条工具消息；结构化笔记对 TODO 持久化；子代理摘要回传，对分层规划器的分叉合并。差异是他们的子代理已产品化，我的在路线图——这个对照本身就是个好话题。

**F8. Terminal-Bench 是什么、为什么实现它的适配？**
终端任务基准：给 agent 一个真实终端完成复杂任务，测试守护进程判分。他们公布全阵营平均只有 36%，而且刻意不做在线榜单——防止对公开题集过拟合。这个立场和我的冻结加登记同源。我的适配器兼容常见任务格式、隔离工作区、命令判分；另有离线冒烟模式让没网也能验证链路。

**F9. 这类运行时的终局你怎么判断？（开放题）**
短期模型变强会吞掉一部分运行时复杂度，但三类不会被吞：安全边界（授权审计是组织需求，跟能力正交）、可验证性（是信任问题，模型越强越需要）、状态治理（是工程问题）。模型越强，"证明它做对了"越值钱——这是我押注评测治理的原因。

### G. 开发过程与踩坑（故事库）

**G1. 最难的一个 bug？**
新版 openai 库的流式接口漏了等待：调用返回的是一个协程对象，直接迭代就炸。藏得深是因为旧版行为不同、测试替身恰好模拟旧行为——单测全绿，真实调用必炸。教训两条：升级 SDK 后测试替身的行为假设全部失效；修复做成双形态兼容，而且先用真实网关冒烟再上量。同一批还修了一个分层不一致：配置层支持自定义供应商，命令行入口的参数校验却把它拒了——配置层说了算，入口层不该有第二套判断。

**G2. Windows 兼容的坑？**
一串：浅克隆的提交只在临时引用里、本地再克隆拿不到——挂分支固定；被杀的 git 进程留下锁文件；Python 3.12 删了老模块、新版本工具链又删了另一个老模块、老项目用了被 3.13 删掉的标准库——解释器级不可修，只能按版本过滤任务；临时索引文件零字节被 git 当损坏。这些堆起来就是官方基准用每题一个 Docker 的原因——本地单环境有天花板，我把它写成数据集口径而不是假装解决了。

**G3. 并行跑两个模型的评测，风险怎么评估？**
共享的可变资源只有 Python 环境（agent 可能自己装包）：串行是先后污染、并行是竞态损坏——概率低、可辨别、可补跑；报告、工作区、仓库镜像全隔离；付费网关两路并发没压力。收益是时长减半。但两轮必须同一份代码（报告记录提交指纹，连未跟踪文件都算脏）——所以改代码必须等两轮跑完，这个约束让我把一个修复推迟了几小时。

**G4. 评测中渠道挂掉的经历？**
mini 档跑到最后四题，渠道连续 503（那个模型后来整个下架了）。当场决策：不中断主跑（四十九次有效数据保住）、失败尝试保留原始记录事后修正口径、设三十分钟探测准备自动补跑。事后把教训固化成代码：服务器错误归基础设施失败。数据事故的标准处理就是三步——保真原始数据、修正口径留痕、机制化防再犯。

**G5. 为什么做这个项目？**
用各类编码 agent 的三个痛点：长任务跑着跑着上下文炸了；工具一多就不敢让它自动跑；说"已完成"但根本没做完。市面工具各解决一角，我想把"持续、可控、可验证"做成一等公民，再用可复现的评测证明这些机制的价值——不是又一个壳子。

**G6. 最诡异的挂起 bug？**
MCP：官方 SDK 的会话对象必须以异步上下文管理器的方式进入才启动后台消息泵，裸构造它，初始化就无声无息地挂死——没有任何报错。定位靠读 SDK 源码看它什么时候起后台任务。附带修了事件循环绑定问题。教训：异步库的生命周期语义是文档盲区，得看源码。

**G7. 被自己的边界判断咬过的例子？**
两个：数据库工具的路径前缀判断（见 D1）；蜂群评审的判定早期匹配裸的"失败"字样，工人汇报"没有测试失败"被误判驳回——改成显式短语加双信号默认不放行。共同教训：字符串匹配的对抗面比想象大，测试要包含"语义相反但包含关键词"的样本。

**G8. 一个月两万五千行还带六百多个测试，怎么做到的？**
诚实版：AI 辅助开发为主，我做架构决策、边界设计和审查——这本身就是这个项目的论点之一：运行时的价值就是让模型在长任务里可控可验证，我用自己吃自己的狗粮。节奏靠三件事：协议先行（接口稳定后实现可以并行推进）、清单驱动（对着二十项审计清单补，不发散）、测试即规格（每块先定可验证行为）。两百多次提交的粒度本身就说明工作流是连续小步交付。

### H. 八股与场景题（结合项目怎么答）

**H1. 为什么工具执行用超时包装而不是信号量？**
超时管单次调用上限（一个工具最多两分钟），并发度管理交给场景（只读并发、写串行）——两者正交。取消传播：超时取消内部任务，清理靠finally；用户级取消是标志位在安全点检查——边界取消更可控，代价是不够即时。

**H2. dataclass 和 Pydantic 各用在哪？**
dataclass 用于进程内数据（消息、响应、事件——热路径零开销）；Pydantic 用于信任边界（配置进来必须校验加报人话错误）。原则一句话：验证发生在边界，内部结构体信任已验证的数据。

**H3. 原子写怎么做的？**
临时文件加同名替换——替换在同分区上是原子的。反例场景：进程死在写会话文件的半路，半截文件让恢复永久失效；替换保证读者要么全旧要么全新。所有持久化统一这一套。

**H4. 子进程的安全注意什么？**
永远传参数列表不走 shell 字符串（git 工具还限定只读子命令白名单）；Windows 上显式用 UTF-8 加容错解码（默认编码会炸中文和表情）；超时必须显式（挂死的 git 拖死整个任务）；捕获输出防污染终端。

**H5. 场景：让 agent 自主跑一百个任务的批处理，怎么做？**
直接答已有的加缺的：任务级隔离（每题独立目录加独立实例，已有）；失败分类先行（基础设施、模型、阅卷分开统计，已有）；断点续跑（没有机制化——报告里有粒度可手工恢复，是改进项）；成本护栏（token 预算有、美元级熔断没有，该加）；渠道健康探测加重试调度（有分类基础，调度可做）。承认缺的比编造全的强。

**H6. 场景：模型输出被注入了"忽略之前指令"，你哪层拦？**
四层递进：标注（外部内容包起来、提示模型当数据）——输出扫描加警告——就算被骗，要执行的动作还要过授权这道独立关卡——决策留审计。承认没有语义级检测，对抗场景靠红队回归。

**H7. git 底层命令那套为什么不用 stash？**
我的快照全用底层命令：树对象存内容、提交对象加元数据、挂引用防回收、恢复时把树写回索引和工作区。stash 会动用户的工作区状态——快照的铁律是零副作用。挂引用还防垃圾回收：只有不可达对象才被清，挂上引用就可达。

**H8. 并发分发的异常语义，哪两处用了"异常不传播"？**
事件广播（单个订阅者出错只记日志——观测不能杀主流程）和只读工具预取（一个搜索超时不该丢掉其他结果）。默认的快速失败在这两个场景都不对：一个要隔离故障面，一个要尽力而为。写和执行类工具串行，异常就地转成观察结果喂回模型——错误也是上下文。

**H9. GIL 对这个项目有影响吗？**
瓶颈结构决定了没有：runtime 是输入输出密集（模型接口、子进程、网络），单线程事件循环够用；计算重的活（git、跑测试）全在子进程里天然绕开；语法解析有缓存摊销。真正做过的性能优化是只读并发和惰性导入（启动一点九秒降到半秒多），都不靠多线程。

**H10. HTTP 推送断线了怎么办？**
诚实答：事件经广播转发给推送订阅者，断线重连靠会话恢复，但事件不重放——没有做事件序号游标，是已知边界（路线图：会话持久化加重连端点）。命令行入口没这个问题。

**H11. 会话为什么用 JSON 不用 SQLite？**
会话是文档型数据（消息数组），访问模式是整体读写不是查询；JSON 加原子替换就是完整解。SQLite 用在它该在的地方（用户数据库工具），未来的检索索引也可以换它。按数据形状选存储，不是按习惯。

**H12. 分词估算误差对预算控制什么影响？**
估算偏低会超预算才触发保护。对策是保守方向：软限低于硬限、八成阈值提前警告、服务端回执回来立即校准本地计数。预算控制是"宁可少给不可超发"的单向门。

**H13. 场景：把它落地给一个十人团队，第一周做什么？**
模型配置指向企业网关（已有路由切换）；权限规则预置团队策略（已有三态规则）；审计日志对接企业系统（事件已有，加出口）；用他们自己的仓库建评测基线（框架已有）；混合环境确认沙箱后端探测（已有）。第二周才轮到定制工具和 MCP 接入。

**H14. 场景：模型升级后怎么知道行为没退化？**
这就是我的实验框架的场景：同任务集、随机交错两配置、预注册主指标、配对统计、护栏指标（安全违规率）。缺的是连续回归的门禁阈值——预注册模板里有这个字段，要人工定。

**H15. 四个 Python 版本怎么保兼容？**
CI 矩阵（两个系统的两三个版本）跑全量测试；版本声明解决不了的（老项目用了被删的标准库）在任务集层面过滤并记录口径。经验：兼容性问题的主源是依赖树不是语言本身。

### I. 取舍与反思

**I1. 最不满意的三件事？**
检索的分词只认英文标识符（中文仓库退化）；HTTP 服务的会话是内存态（和命令行的恢复能力不对齐）；可视化缺位（事件数据都有、时间线没渲染）。三个都在路线图，优先级让位给 Aider 对照。

**I2. 做错了什么？**
早期阅卷的"已验证"有水分却没发现——更早做标准答案入库的话，早期两轮"测试未过"的结论会更干净。教训：验证器本身需要被验证——阅卷员的阅卷员是标准答案。

**I3. 重做会改什么？**
事件结构第一天就版本化（现在加字段要兼容旧报告）；测试替身少模拟 SDK 边界（流式 bug 的教训，集成冒烟该更早进 CI）；评测环境第一天就定每题容器的路线——Windows 单环境的天花板花掉的时间够搭容器了。

**I4. 下一步计划？**
Aider 跨运行时对照（同题同阅卷，把"有数字"变成"运行时能力证据"）；模型侧的子任务委派工具；事前拦截钩子。

**I5. 四十二处技术债标注是什么机制？**
仓库约定：每个"刻意简化但有明确天花板"的实现必须带标注注释，写明天花板和升级路径（比如"检索每次全仓重扫，大仓该换持久索引"）。价值：债显式化——面试里这就是现成的"你最懂的局限"清单；工程上防止简化悄悄变成债。

**I6. 最想重写的一块代码？**
主循环文件（一千一百行）：循环、压缩、修复、预取耦在一个类里。方向是拆成主循环上的显式阶段。但现在动它风险大于收益——它是测试覆盖最密的路径，等子代理工具要动上下文管理时一并重构。

**I7. 一个人项目怎么做代码评审？**
三道替代机制：架构边界的机器检查（依赖方向）；对照审计清单（标准先行）；评测即评审（行为级回归：红队、标准案例、冻结跑分的契约测试）。人的评审缺位用可执行的规格补——不完美，但比没有强。

### J. 行业认知（展示你不只写代码）

**J1. 上下文工程是什么？和 RAG 什么关系？**
构造对模型最有效的上下文窗口的过程——有个好比喻：系统提示是内存、压缩是磁盘换页、笔记是持久化的工作集。核心矛盾是信息越多注意力越稀。RAG 只是它的一个子问题（检索什么），完整的问题还包括保留什么、压缩什么、记到哪。我的实现把这几个子问题拆成了检索、分区、压缩、记忆四个组件——就是这个词的工程化形态。

**J2. 提示注入业界共识到哪了？**
被引用最多的定义（Simon Willison）：把不可信文本和可信提示放进同一个窗口，模型可能执行前者。共识：这是架构级问题不是 bug、没有完全解；分隔符是弱防御；主流缓解是输出过滤和模型层分类器。我的立场与业界一致：工具层授权是纵深里最可靠的一层——注入骗得了模型、骗不过独立的授权判定；其余层做降幅、不做承诺。

**J3. agent 记忆的研究方向？**
产品化三条线：上下文内记忆（压缩加笔记）、检索式记忆（跨会话向量召回）、参数化记忆（微调）。工程上的真问题是信任与污染：什么时候该忘、什么该隔离、什么可共享——我的四层隔离和漂移校验就是我对这个问题的答案。

**J4. 多 agent 是不是比单 agent 好？**
分场景。业界经验（Anthropic 的多 agent 系统）：子代理花几万 token 返回一两千摘要，是"用 token 买隔离的上下文"，适合探索广度型任务，不适合深度依赖型。我的实践：默认单 agent 简单循环；分层和蜂群两种多 agent 按任务显式选——判断标准是子任务耦合度，不是"多"的时尚。

**J5. 基准过拟合怎么防？**
Terminal-Bench 的立场最典型：不做在线榜单、定期换题——公开题集必然被优化目标污染。我的机制同构：题集指纹入库、登记不可变、预注册主指标（先声明后看数）。评测可信度的敌人一半是模型，另一半是做评测的人自己。

**J6. 模型能力涨这么快，运行时会不会白做？**
不会白做的恰好是我花力气的地方：授权审计（组织合规需求，与能力正交）、评测（信任问题，越强越需要）、状态恢复（工程问题）。会被吞的部分我承认：编排的价值在缩水、工具脚手架在简化。所以路线图把资源押在评测治理和跨运行时对照上——那是复利部分。

### K. 压力测试（准备好就不慌）

**K1. "40% 到 55% 的分数也太难看了吧？"**
先给语境再给立场：榜单头部是官方环境 79%、一百行代码的极简环境 65%；我的数字出自本地 Windows、第三方网关、自建阅卷、二十题——不可比也无需比。这次跑的产出不是分数，是三件事：链路可信（一百八十次尝试全部外部验证、阅卷零故障）、误报率第一次被量化、口径完整。分数难看的是模型，不是我。

**K2. "一个人一个月的项目，凭什么信？"**
看可验证性不看人：六百多个测试、架构边界进 CI、评测报告带代码指纹、四十二处显式技术债、登记不可变——每个论断都能在仓库里指到出处。这个项目本身就在回答"怎么信任一个 agent 的工作"，我用同样的标准要求自己。

**K3. "第三方网关的模型你确定是真的吗？"**
不确定，且写进了口径红线：模型真实性不可验证、最高档反常不高于中档但区间重叠不显著。这正是"数字证明链路、不证明排名"的原因。要能力结论需要官方接口加官方环境加更大样本——预算允许的话是下一步。

**K4. "这就是个玩具吧，离生产差多远？"**
按优先级数：HTTP 会话持久化、事前拦截钩子、多租户隔离、指标导出。但"玩具"的判断标准错了——单用户本地长任务是我的目标场景，这个场景里它是可用工具；生产化的差距是资源问题不是架构问题——协议边界都在，换实现不改结构。

**K5. "Python 写运行时，性能行吗？"**
算过账：单次尝试八十八到一百三十四秒里，本地开销占比个位数百分比，其余是模型接口和跑测试——优化 runtime 是优化不显眼的百分之五。做过的有效优化：惰性导入、解析缓存、只读并发。真到性能墙的场景（高频小任务批处理）才值得谈常驻进程池——现在没有这个场景。

**K6. "你这不就是又造了个轮子？"**
承认重叠：agent 循环谁都能写，一百行都能拿 65%。我不重复的是三条链：授权链（命令级判险加签名记忆加审计）、评测治理链（冻结加入库验证加误报率加登记）、恢复链（快照加打转回滚加协议修复）——这三条在开源运行时里都稀缺。造轮子的部分是学费，链路是资产。

**K7. "哪个设计你现在觉得是错的？"**
两处：缓冲区的间接层让分区语义和实际数据流不一致，早期还因此修过"填了没人消费"的 bug——重来会做成显式的压缩管道而不是第四个分区；事件结构没版本化，现在加字段要兼容旧报告。能立刻说出具体的错，比"没什么大问题"可信。

### L. 行为面与叙事

**L1. 讲一个你坚持了但被质疑的决定。**
打转只回滚单文件。质疑是"干脆整个工作区重来更干净"。坚持的理由：首次触发时只有那个文件被证明是坏的，恢复动作本身也是副作用，整区回滚会把好的半成品一起丢掉——保守恢复，激进留给用户。后来看到 Claude Code 的设计也是这个哲学：显式回滚，不自动大回滚。

**L2. 讲一次你和数据的冲突。**
渠道 503 那次：直觉说"重跑失败的题补上"，数据纪律说"不中断主跑、保真原始记录、修正口径留痕"。选了后者——补跑会造成同一尝试两个版本、破坏可复现性。事后把"服务器错误归基础设施"固化进代码。教训：数据完整性决策要靠事前规则（后来有了预注册模板），不能靠临场判断。

**L3. 从失败里学到最重要的东西？**
验证器本身需要被验证。阅卷环境坏掉时给出的"测试未过"和真实失败不可分——我以为在测模型，实际在测我的环境。这个教训泛化：测试、监控、评审，所有"裁判"都需要自己的标准答案。所以我给阅卷员建了标准案例、给评测建了入库验证、给报告建了指纹。

**L4. 为什么值得花一个月？**
按诚实度排：技术上它是我所有兴趣（模型、系统、安全、统计）的交集；职业上 agent 基础设施是明确的增量领域，深水区在运行时不在模型；产品上我自己每天用编码 agent，痛点是真实的。

## 九、口径红线（不能说的话）

- 不说"运行时或模型能力提升百分之多少"——二十题加第三方网关不支持能力结论。
- 不把本地成绩说成官方榜单分数；引用榜单数字必须带"2026 年 8 月快照"和口径。
- 不说 55% 对 40% 是模型能力差异——区间重叠，差异不显著。
- 不说"防住了所有注入"——签名式检测有明确边界。
- 不说沙箱"完全隔离"——默认后端是进程围堵。
- 数字精确性：测试数报"收集 654"；mini 误报率能报双口径（原始 61.9%、有效 72.2%）；总成本 99.91 美元。
- 被问不知道的：直说"这块我没做或没测过，边界是什么、升级路径是什么"。
- 被 AI 辅助开发问住时不否认也不渲染：架构、边界、审查是我做的——这正是项目论点的一部分。
