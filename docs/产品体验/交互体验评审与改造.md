# Synapse 交互体验评审与改造

## 目标

让用户在首次启动、长任务执行、授权确认和任务收尾四个阶段都能清楚知道系统正在做什么、能否中断、是否需要确认，以及结果依据是什么。

## 已完成改造

| 场景 | 设计与实现 |
|---|---|
| 首次启动 | 向导负责模型选择与密钥输入，不回显 API key；无配置时给出可恢复的下一步。 |
| 主界面 | 根据终端宽度降级展示品牌、模型、规划模式和会话信息，避免窄终端截断。 |
| 执行过程 | Rich live 面板展示当前阶段、工具、Token、耗时和确认状态；plain fallback 保持等价信息。 |
| 授权确认 | 区分操作风险与参数，支持明确确认和取消，确认面板不被 spinner 覆盖。 |
| 收尾 | 同时展示 Agent 状态、外部验证状态和运行评分，避免把模型自报成功当成功能成功。 |

## 设计约束

- CLI 是工作台，不做营销页式大卡片或无关装饰。
- 工具型操作优先使用图标、快捷命令和紧凑状态，不用冗长说明代替反馈。
- 流式输出、取消和后台任务必须可回收，错误应告诉用户可执行的下一步。
- CLI、HTTP 与 Library API 共用事件和结果语义，避免同一任务在不同入口出现矛盾状态。

## 当前边界与后续

- 历史任务浏览和更完整的 Web 视图仍未实现；先复用现有 session 与 event API。
- 不引入重型 GUI 框架或多端实时协同，除非有明确用户场景和维护预算。
- UX 变更需要覆盖宽、中、窄终端及 plain fallback 的快照或自动化检查。
